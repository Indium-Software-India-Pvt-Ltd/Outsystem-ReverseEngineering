# OutSystems now ships its own extraction API

**The single most consequential finding is that you probably should not build an OML parser at all.** In 2026 OutSystems shipped the Service Studio MCP server — a local HTTP server embedded in Service Studio 11.55.91+, started from `Edit > MCP Configuration...`, listening on `http://127.0.0.1:41820/mcp`, fronted by a first-party MIT-licensed skill repository at [OutSystems/outsystems11-mcp](https://github.com/OutSystems/outsystems11-mcp) — whose **read tools are Generally Available** and which exposes the previously-internal OutSystems Model API to any coding agent ([OutSystems MCP in O11 and ODC](https://success.outsystems.com/documentation/11/outsystems_mcp/outsystems_mcp_in_o11_and_odc/)). That path reads entities, attributes, foreign keys, structures, server and client actions, screens, web blocks, roles, variables, settings, events, integrations, timers, exceptions, locales, images, resources, scripts, email templates, external sites and themes — the whole intra-module surface that DIY OML parsing was invented to reach — and it does so with vendor blessing, which sidesteps the one genuinely contested legal question in this whole area. Separately, and independently, the `.oap`/`.oml` container format *is* fully decoded: direct measurement of the user's own `Test Application.oap` confirms a plain ZIP wrapping a readable `Manifest.xml` and an `.oml` that is **not encrypted** — ASCII magic `OML`, a uint32 little-endian header length, 36,219 bytes of plaintext pipe-delimited header, then a raw-DEFLATE stream inflating to 93 concatenated Fast Infoset documents with byte-exact self-consistency. So the format is open, the API is supported, and the only genuine engineering gap is **headless batch extraction**, because the MCP server is Windows-bound, reads one module at a time, must be started manually per session, and is an interactive tool wearing an API's clothes. Everything downstream of extraction — logic translation, UI fidelity, migration effort — rests on an evidence base that is thin, vendor-skewed and entirely unquantified: there is no neutral, named-client, quantified public case study of an OutSystems-to-modern-stack migration, and no published person-months-per-screen figure exists anywhere. On the specific question of `morluto/rea`: it is a 0% fit for the `.oml` work and its own skill tells agents to skip it for source-repository analysis; treat it as an optional, unproven secondary lane.

## The supported model-read path landed in 2026 and largely obsoletes DIY OML parsing

OutSystems' own documentation now describes the mechanism plainly: the MCP host connects to a local MCP server running inside Service Studio, writes C# that uses the OutSystems Model API, and sends that code to the server, which runs it against a copy of the module ([OutSystems MCP in O11 and ODC](https://success.outsystems.com/documentation/11/outsystems_mcp/outsystems_mcp_in_o11_and_odc/)). The server **ships in the standard release with no separate build or activation**, and is registered with a one-liner such as `claude mcp add --transport http servicestudio http://127.0.0.1:41820/mcp --scope user` ([OutSystems/outsystems11-mcp](https://github.com/OutSystems/outsystems11-mcp)). The support split is explicit and worth internalising before planning anything: **reads are GA, writes are Beta** — the skill itself calls the write set a non-final capability provided to collect customer feedback and instructs agents to point users at the beta-features agreement on first write use ([servicestudio-mcp-oml/SKILL.md](https://raw.githubusercontent.com/OutSystems/outsystems11-mcp/main/servicestudio-mcp-oml/SKILL.md)).

The read surface is large and specific: `getDataModel`, `getStructures`, `getActionNames`, `getServerAction`, `getClientAction`, `getServiceAction`, `getScreenNames`, `getScreen`, `getWebBlockNames`, `getWebBlock`, `getRoleNames`, `getRole`, `getClientVariables`, `getSessionVariables`, `getSettings`, `getEvents`, `getEventHandlers`, `getIntegrations`, `getTimers`, `getUserExceptions`, `getRoleExceptions`, `getLocales`, `getException`, `getImage`, `getResource`, `getScript`, `getEmailTemplate`, `getExternalSite`, `getTheme`, plus Traditional Web variants and — most interesting for bulk export — `getSerializedObject`, `getSerializedObjectByKey`, `getSerializedObjectByNameAndType` and a ModelQL query verb `runQuery` whose queries must start with `Root { … }` ([SKILL.md](https://raw.githubusercontent.com/OutSystems/outsystems11-mcp/main/servicestudio-mcp-oml/SKILL.md)). The sandbox is tight: no `Console`, no `System.`-qualified names, no reflection, no file, process or network access; debug inspection is done by throwing an exception whose message begins `PROBE:`; `applyModelApiCode` times out at **300 seconds**; attribute names are truncated to **28 characters**; new cross-module dependencies cannot be added through the API at all. Authentication is an interactive local trust handshake — Service Studio prompts on first command — and all writes are staged through the interactive Compare-and-Merge window.

The limitations are the build case. The server reads *the module currently open in Service Studio*, on a Windows desktop, with the server manually started, one module at a time. Nothing in the official stack gives you "point at a 400-module factory, get the logic as JSON." That is the one genuine gap worth engineering around, and it is an orchestration problem (drive Service Studio, or drive `OutSystems.Model.V1.dll` directly) rather than a format-reverse-engineering problem. The undocumented-but-real alternative is to reference the Service Studio assemblies from your own .NET 8 process, which the community `oml-cli` does: `$(SS)\OutSystems.Model.V1.dll`, `$(SS)\OutSystems.Model.Plugins.dll`, `$(SS)\ServiceStudio.PluginAPI.dll`, `$(SS)\ServiceStudio.Framework.dll`, `$(SS)\ServiceStudio.Common.dll` and the plugin assemblies, all rooted at a default `C:\Program Files\OutSystems\Service Studio 11\Service Studio` ([OmlCli.Core.csproj](https://raw.githubusercontent.com/Topurrra/oml-cli/main/src/Core/OmlCli.Core.csproj)); `oml-cli` states it uses your locally installed Service Studio assemblies, does not ship them, reads and changes modules through the typed Model API, and **never edits OML XML** ([oml-cli](https://github.com/Topurrra/oml-cli)). Treat that route as at-your-own-risk and pinned to an exact Service Studio build: OutSystems publishes no reference, no NuGet package and no compatibility contract for direct assembly consumption. Three assembly names circulating in the original brief — **`OutSystems.Model.Reader`, `OutSystems.Common` and `OutSystems.ObjectKeys` — could not be confirmed by any source** and should be treated as unverified until someone directory-lists a real install.

## The .oml container is decoded, unencrypted, and version-stamped in plaintext

This section leads from direct, reproducible measurement of the user's own `Test Application.oap` (3,096,013 bytes, created 2026-10-21), cross-verified twice, rather than from the web. An earlier revision of that measurement was wrong and has been retracted: it concluded the `.oml` was uncompressed, having searched for a deflate stream only within +64 bytes of the magic when the plaintext header is 36,219 bytes long and the compressed stream therefore begins at offset 36,226. **The file is raw-DEFLATE compressed.** The "not encrypted" half of the original conclusion stands.

The `.oap` is a plain ZIP with no password and no OutSystems wrapper, whose archive comment is the literal string `The Solution Pack Manifest` — a clean fingerprint. It holds three entries: `Manifest.xml` (186,445 bytes), a directory named after the solution, and `Test_Application/TestApplication.oml` (3,053,090 bytes). `Manifest.xml` is readable UTF-8 XML requiring zero tooling, rooted at `<Pack Schema="3" HubServerVersion="11.42.1.47790" LastUpgradeVersion="11.0.0.200" IsApplicationPack="true" …>` and carrying the module inventory, the eSpace reference graph, `ApplicationKind="CrossDevice"`, `PrimaryColor`, `TemplateKey`, `APIHash`, `ContentHash`, `OriginEnvironmentCode`, stable UIDs and the app icon as inline base64 PNG. `IsApplicationPack` is the `.oap`-versus-`.osp` discriminator. One hundred eighty-six kilobytes of manifest for a *single-module* app is explained by the manifest carrying the full reference closure.

The `.oml` layout, measured:

| Offset | Size | Content |
|---|---|---|
| `0x00` | 3 | ASCII magic `OML` (`4F 4D 4C`) |
| `0x03` | 4 | uint32 **little-endian** header length = `0x8D7B` = **36,219** |
| `0x07` | 36,219 | plaintext ASCII, `\|`-delimited header |
| 36,226 | 3,016,864 | **raw DEFLATE** (`wbits=-15`; no zlib `78 9C`/gzip wrapper) |

`zlib.decompressobj(-15)` on the remainder inflates cleanly to **8,185,876 bytes** with `unused_data` empty — the whole post-header remainder is one deflate stream, 2.68× the file. The inflated blob splits into an unidentified 1,492-byte preamble (containing a 93-byte high-entropy block prefixed `5d 00 00 00`, purpose not determined and not guessed at), a **fragment directory** at bytes 1,492–5,523 holding 93 records of `[uint32 nameLen][name ASCII][uint32 contentLen]`, and 93 concatenated **Fast Infoset** documents (ITU-T X.891 / ISO-IEC 24824-1 binary XML, [Fast Infoset](https://en.wikipedia.org/wiki/Fast_Infoset)) from byte 5,524 to EOF, each beginning `E0 00 00 01`. The framing is proven rather than guessed: Σ(contentLen) = 8,180,352, the directory ends at 5,524, and 5,524 + 8,180,352 = 8,185,876 = len(blob) exactly, with 93/93 bodies carrying the FI magic and zero slack.

Two measured facts dominate pipeline design. First, **the version triple lives in the plaintext header and costs nothing to read** — `11.0.415.100|11.55.93.65333|155|Am0mHuuAS0yPh37L4weNBQ|…` gives OML/model version, producing platform version, revision and the eSpace UID, and that UID matches the `Reference UID` in `Manifest.xml`, confirming the manifest↔oml join key. A pipeline can therefore version-gate every file before attempting to inflate it. Second, the `References` fragment is **5,368,717 bytes — 65% of a trivial module** — because it embeds every producer's public interface; `Resources` is another 1,971,193. Extracting a module's *own* fragments and resolving references separately is not an optimisation, it is the difference between a tractable and an intractable pipeline.

Encryption is absent. Inflated entropy is ~6.37 bits/byte over the first 200 KB (versus ~7.99 for ciphertext), the 36 KB header is plain ASCII, and the body inflates with a stock raw-deflate call and no key. The inflated blob contains 112,668 printable-ASCII runs of ≥12 characters. The widespread community belief that only Service Studio can read an OML — stated on the forums as the only way to read or edit an OML being Service Studio or ODC Studio ([OML data](https://www.outsystems.com/forums/discussion/100942/oml-data/)) — **is simply wrong**; the format is protected by obscurity and binary-XML encoding, nothing more. It also resolves a real community conflict in which one contributor calls OML a binary format and another calls it XML on the very same thread: both are right at different layers, the container being binary and the content being XML in Fast Infoset encoding. OutSystems' own engineering content describes the model as having an in-memory representation as C# class instances and an XML-based persistent representation, the OML being a compressed file composed of several fragments ([DEV: The OutSystems Model](https://dev.to/outsystems/the-outsystems-model-abstracting-low-code-into-a-visual-language-498p)) — which the measurement confirms exactly. Neither BinaryFormatter nor protobuf appears anywhere; the only .NET-style serialization present is Newtonsoft.Json with `$type`/`$id`/`$ref` in the header's final base64 field, and that is Service Studio *presenter state*, not the model, leaking internal namespaces `OutSystems.MetaModel`, `OutSystems.MetaModel.CompoundKeys.RootCompoundKey`, `ServiceStudio.Presenter` and `ServiceStudio.Framework`.

What remains hard is clearly delimited. Decoding Fast Infoset to a true XML tree needs a real decoder — Python has no stdlib support, and the community tool bundles `Noemax.FastInfoset.4.1.5.dll` and `Noemax.FastInfoset.Net4.18.14.5339.dll` for exactly this reason. A plain `strings` pass over the fragments already recovers real content (structure `MasterDetailItem` with its attributes, client action `OfflineDataSync` with `IsAsync` and input `SyncUnit`, client variable `LastURL`, the default theme, default screen `MainFlow\Screen1`, the global error handler path and every validation message), but types are not inline — they are key references with a `%` sigil, e.g. `Type: %H6G+eTAigEi7LPUbg3Ey0g` — so a correct parser must build a key→object map across all fragments. Hardest of all, **expressions are stored as pre-parsed `ParsedExpression` ASTs with type-by-key references**, so recovering readable expression *text* means re-serializing an AST, not reading an attribute. That should be scoped explicitly rather than assumed. Finally: the brief's `.oar` extension appears to be a **false premise** — targeted searching found no source describing `.oar` as an OutSystems format at all, while `.osp` is well attested as the same container shape describing a multi-application solution, and officially so, since the Solution Pack Tool `osptool.exe` accepts either an `.osp` or an `.oap` ([Solution Pack Tool command line reference](https://success.outsystems.com/documentation/10/setting_up_outsystems/unattended_installation_and_upgrade/unattended_installation_and_upgrade_for_java/solution_pack_tool_command_line_reference_for_java/)).

LifeTime v2 is the right factory-level starting point and the best machine-readable contract in the set: the base URL is `<lifetime-domain>/lifetimeapi/rest/v2`, v2 adds deployment zones, users, teams and roles over v1, every operation is bounded by the service account's LifeTime permissions, and a live Swagger definition is served per instance at `https://<LIFETIMEURL>/lifetimeapi/rest/v2/swagger.json` ([LifeTime API v2](https://success.outsystems.com/documentation/11/reference/outsystems_apis/lifetime_api_v2/); [CrossLifeTimePromotion](https://www.outsystems.com/forge/component-documentation/25715/crosslifetimepromotion-o11)). Pull that file from the target instance rather than trusting docs. Critically, **LifeTime v2 supports binary `.oap` up/download for cross-infrastructure deployment from LifeTime 11.22.0+**, which makes it the sanctioned programmatic artifact-acquisition path; there is no documented HTTP URL for scripted `.oml` download, and scripting the Service Center button would mean session-cookie scraping of an undocumented ASP.NET endpoint.

Two cautions on the metamodel. First, the officially-listed tables are `OSSYS_APP_DEFINITION_MODULE`, `OSSYS_APPLICATION`, `OSSYS_ENTITY`, `OSSYS_ENTITY_ATTR`, `OSSYS_ENTITY_RECORD`, `OSSYS_ESPACE`, `OSSYS_ESPACE_ENTITY`, `OSSYS_ESPACE_TENANT` and the `OSSYS_BPM_*` family, and the list is explicitly marked incomplete; `OSSYS_ENTITY` is the only table whose contents are described, holding the mapping between physical and logical entity names. Three names from the original brief — **`OSSYS_MODULE`, `OSSYS_ESPACE_REFERENCE` and `OSSYS_APP_DEFINITION` — were not confirmed**, and the docs show `OSSYS_APP_DEFINITION_MODULE` and `OSSYS_ESPACE_ENTITY` instead; O11 calls modules "eSpaces" at the DB level, so `OSSYS_ESPACE` is likely the real table. One researcher did see `OSSYS_MODULE` cited as internal-use-only in a second official page, so the conflict is live — verify against a database before asserting it. Second, a former OutSystems staff member stated that configuration tables are on the roadmap to be rewritten and most are likely to be modified or removed in the next majors ([Extended Metamodel thread](https://www.outsystems.com/forums/discussion/95091/extended-metamodel-extendedmetamodel/)) — a concrete signal that a DB-level tool carries real maintenance cost. The twice-renamed Code Quality API, with a hard cutover deadline of 31 December 2024 for the old `ArchitectureDashboardAPI` address, is the same lesson applied to a *supported* API.

**ODC closes most of this.** Modules do not exist — the equivalent concept is an asset ([ODC for O11 developers](https://success.outsystems.com/documentation/outsystems_developer_cloud/odc_for_o11_developers/)). `.oap` export is not a thing in ODC per community answer, though that thread does not settle it and the wording looks possibly garbled. ODC's public REST APIs span 12 domains and the relevant trio — Portfolio v2, Dependency v1, Asset v1 — is strictly portfolio-level: what assets exist, their revisions, how they depend on each other, and nothing published indicates intra-module logic. There is **no public per-module model-reading API in ODC** equivalent to O11's Model API; the ODC MCP server is cloud-mediated rather than an inspectable local surface. No official ODC packaging specification was found, no ODC CLI was found documented (a genuine unknown, not a negative finding), and ODC moves the database to Aurora PostgreSQL, invalidating the SQL-Server-specific leg of any data pipeline. The practical rule: **O11 self-managed is the permissive case, O11 cloud degrades to client-side plus database plus metadata, and ODC degrades further to client-side plus in-app metadata.**

## Generated source sits on disk, so decompilation is the fallback — and "no source export exists" is false

Two researchers appeared to disagree about decompilation, and the disagreement dissolves once stated precisely. One found official documentation that **a self-managed Platform Server retains a full Visual Studio project with generated `.cs` source** on every publish, no flag required: `<platformserver>\share\<modulename>\full` is the full compilation cache on the Deployment Controller and contains generated source (`.oml`, `.cs`, `.csproj`), release binaries (`.dll`, `.aspx`, `.asmx`) and web resources, while `<platformserver>\running\<modulename>.<versionid>` on each front-end holds only binaries and resources, with shared DLLs hard-linked into `repository` ([guide to disk space usage](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)). OutSystems' own SAST guidance, quoted in the forums, tells customers the source code can be found at `<PlatformInstallationFolder>\Platform Server\share\<ModuleName>\full`, that the folder holds a Visual Studio .NET project with generated C#, ASPX, CSS and JavaScript, and that customers can run SAST tools against it — while also stating that **source code can only be extracted with a self-managed installation** ([forum 61645](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/)). The other researcher found **no source showing ILSpy/dotPeek on OutSystems assemblies as a practised technique**, and concluded decompilation should not be asserted as viable without testing. Both are correct: **if the source is on disk, you do not decompile.** Decompilation only becomes the route when you hold binaries only — a front-end-only foothold, a copied `running\` or `repository\` folder, or an extracted mobile shell. That also explains the literature vacuum: for the population with access, decompilation is redundant; for the population without it, the binaries are unreachable. No conference talk, security-research post or dedicated GitHub tool on decompiling OutSystems-generated code surfaced across multiple search formulations — report that as "none found as of October 2026," not "none exists."

Where binaries *are* all you have, the output is ordinary managed code with no obfuscation documented anywhere, and forum practitioners report decompiling it with dotPeek and Reflector ([forum 40860](https://www.outsystems.com/forums/discussion/40860/is-it-possible-to-get-the-deployed-codesystem-generated-c-codes/)), so ILSpy/dnSpy/Rider should work with no special handling and `ilspycmd -p` emits a compilable project ([ilspycmd](https://www.nuget.org/packages/ilspycmd)). Two contradictory readability opinions on that same thread reconcile the same way the source-versus-decompile question does: identifiers survive (one contributor states the generated code shows your screen, entity and attribute names), while structure is machine-shaped — so the code is greppable and analysable but unpleasant to maintain. The *verified* naming fingerprints are `OutSystems.Nss<ExtensionName>` for extension namespaces, `R`-prefixed record wrapper types, and a `<ModuleName>ReferencesProxy` project in the detached solution. The commonly repeated **`ssModuleName` / `rssModuleName` DLL convention could not be verified from any source** despite repeated site-restricted searching, and should be treated as unverified folklore pending direct inspection of an assembly. Whether PDBs accompany the DLLs is also unverified, which matters because PDBs would bring decompiler output much closer to the generated source.

The third conflict is the most important to settle, because it is a vendor-interest conflict rather than a technical one. A migration-vendor blog claims OutSystems apps compile to a proprietary runtime with no source export ([rapidevelopers](https://www.rapidevelopers.com/md/no-code-to-code/how-to-migrate-outsystems-project-to-code)), and a review site asserts that neither O11 nor ODC provides any source-code export that runs outside OutSystems ([RapidDev](https://www.rapidevelopers.com/review/outsystems)). **Both are contradicted by primary sources.** OutSystems' own detach documentation describes a standard, readable .NET solution with a documented folder structure, built with Visual Studio 2022 against .NET Framework 4.7.2 minimum, published to IIS, requiring Platform Server 11.18.1+, applying to all applications at once, and irreversible ([The detach process for OutSystems 11](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)) — and MSA §8.4(ii) grants the entitlement contractually. Prefer the primary sources and name the contradiction: these are commercially interested parties selling the conclusion that exit requires their services. (Note also that one researcher's fetch of the detach documentation returned HTTP 404 while another's succeeded, so the page is live but flaky.)

Fidelity of the detached projection is well documented and bounded. Each module project's subfolders are `Actions`, `Blocks`, `Entities`, `Structures`, `ProcExc<ProcessName>`, `Exceptions`, `Roles`, `TypeFactory`, `WebServices`, `WebReferences`, under a `.sln` — a near-1:1 projection of the element tree, so named model elements, action bodies, emitted SQL, roles, exception handlers and web-service contracts are recoverable. What is *absent from generated code entirely* is the visual layer: node coordinates, flow layout, descriptions, comments and the design-time widget tree — those require the `.oml`. OutSystems states the losses plainly: Service Studio, Integration Studio, Service Center, LifeTime and their visual development, ECT, monitoring and deployment features all go; timer management reverts to direct database work; cross-module references must be managed by hand-copying DLLs; the Scheduler Service source is provided only on request; mobile native shells come as a `tar.gz` kept only 7 days after a successful build; and **no database schema or data export is supplied** — the page gives SQL UPDATE statements against metadata tables and connection-string changes, and for cloud customers OutSystems does not provide a clone of the cloud database. On the client side, Reactive Web and Mobile screens, blocks and widgets are generated as React components shipped as optimized JavaScript ([OutSystems blog](https://www.outsystems.com/blog/posts/all-you-need-to-know-about-reactive-web)), and community observation of persistent DevTools source-map warnings suggests **no source maps are emitted** — a single-thread community observation, not an OutSystems statement. The easier client-side surface is not the JavaScript at all but the auto-generated screen-data REST endpoints, which enumerate the server action surface and payload shapes straight from the network tab.

## The open-source landscape is thin, the OML-parser fork lineage is unsettled, and every fork is version-pinned

Exactly one OML parser lineage exists, and the two researchers who looked at it disagree about which fork is live. **Do not pick one.** One reports `kelter-antunes/oml-utilities` as the usable copy — `master`, 19 commits, source read directly — with the GitHub API returning **404 for `caiosm1005/oml-utilities`** on 2026-10-21, suggesting the original upstream behind the Forge asset is gone or renamed ([fork](https://github.com/kelter-antunes/oml-utilities); [Forge OML2XML listing](https://www.outsystems.com/forge/component-overview/10885/oml2xml)). The other reports `silviogarbes/oml-utilities` as the primary — MIT, 4 stars, **last commit 2023-02-09** — and characterises the kelter-antunes repos as low-signal forks (0 stars, last commits 2024-06-11 and 2024-12-20, the second with no README and no licence) ([silviogarbes](https://github.com/silviogarbes/oml-utilities); [library fork](https://github.com/kelter-antunes/oml-utilities-library)). The lineage is unsettled; verify both before depending on either.

What matters more is the risk they share. `oml-utilities` does not reimplement the format — **it reflects into OutSystems' own shipped DLLs**, embedding `OutSystems.Common.9.1.603.0.dll`, `OutSystems.Common.10.0.303.0.dll` and `OutSystems.Common.11.0.520.0.dll` with matching `OutSystems.RuntimeCommon` versions, plus the `Noemax.FastInfoset` and `ICSharpCode.SharpZipLib` pairs that independently corroborate the FI-over-DEFLATE stack. Its README states that any read or manipulation must specify the target platform version in order to load the correct DLL assemblies for decoding, and its load path contains an `UnsupportedNewerVersion` exception — OutSystems' own loader refuses OMLs newer than the assembly. **The user's file was produced by platform `11.55.93.65333` with OML format version `11.0.415.100`, against an embedded `11.0.520.0`**, so "UnsupportedNewerVersion on current O11 files" is not a hypothetical. That version coupling, the disappearance of the upstream repo and the withdrawal of the Forge OML↔XML converter (an MVP states flatly that the component was removed, on the [OML data thread](https://www.outsystems.com/forums/discussion/100942/oml-data/)) together make the clean-room route — deflate plus Fast Infoset plus the fragment framing measured above — the more durable one for file-based work, and the MCP route the more durable one for logic.

## The migration evidence base is vendor-skewed, unquantified, and contradicted by OutSystems' own product decisions

Be blunt about this, because the temptation to let vendor claims accrete into apparent consensus is the main intellectual hazard in the topic. **There is no neutral, named-client, quantified public case study of an OutSystems-to-modern-stack migration.** No published person-months-per-screen or per-module effort figure exists from any non-commercial source. No verified AI-migration success rate exists: the entire corpus is one vendor's self-reported numbers on a public Forge sample app, one individual's blog anecdote reporting a React + .NET app generated in a single session from an OutDoc export ([Medium](https://medium.com/@avidas.ca/how-i-turned-an-o11-app-into-react-net-without-rewriting-a-single-line-by-hand-17611902f8e1), itself returning 403 to automated fetch), and academic work that **reports no accuracy, precision, recall or success-rate figures at all** while stating that LLM output is nondeterministic so completeness and correctness are not guaranteed, that only data models were implemented, and that in its own demos some elements are missing or wrong, typically associations ([arXiv:2412.05075v1](https://arxiv.org/html/2412.05075v1)). A critical literature review on OutSystems exit readiness exists on [ResearchGate](https://www.researchgate.net/publication/407425757_The_OutSystems_Low-Code_Platform_Between_Vendor_Promises_and_Practical_Evidence_A_Critical_Study_of_Scaling_and_Exit_Readiness_An_analytical_literature_review_based_on_peer-reviewed_work_and_practitio), but the site returned 403 to automated fetch and its peer-review status is unconfirmed — cite it only as "a literature review exists."

The strongest *indirect* signal is a product decision rather than a claim. In November 2025 OutSystems shipped the **O11→ODC Conversion Assessment Tool**, installed from Forge onto the customer's own O11 infrastructure, which flags code, data and infrastructure patterns that will not carry over — including SQL and database constructs that will not work against ODC's Amazon Aurora PostgreSQL ([product update](https://www.outsystems.com/product-updates/o11-to-odc-conversion-assessment-tool)). It shipped an *assessment* tool, not a conversion tool. The accompanying conversion tooling automates running a conversion plan and reporting per-run status, while leaving manual the verification that each asset is ready, the downloading and adjusting of each converted file, the dependency updates, the TrueChange error fixes, the producer-to-consumer publishing order and the configuration review ([code conversion using the tool](https://success.outsystems.com/documentation/11/outsystems_11_to_odc_conversion/execute_app_conversion/convert_code/code_conversion_using_the_tool/)). **If automated conversion of OutSystems logic were tractable, the vendor with full model access and total design freedom would have shipped it for its own migration path.** That is the right prior for anyone promising automated exit to a foreign stack. For completeness on the within-platform path, OutSystems' own guidance on Traditional-to-Reactive conversion says that if the migration involves significant UX redesign or architectural overhaul, consider building a new Reactive app from scratch rather than converting ([suggested stages](https://success.outsystems.com/Support/Enterprise_Customers/Upgrading/Introduction_to_migrating_Traditional_Web_to_Reactive_Web_Apps/Suggested_stages_of_Traditional_to_Reactive_App_migration)).

Where the evidence *is* strong is data, and it comes from OutSystems itself. The official data-migration guide prescribes a strict nine-step order whose logic transfers wholesale to an exit, with the new stack's database as the destination: inventory source entities by solution/application/eSpace including producer dependencies; match entity and attribute **physical** names via `SS_Key` paired with the eSpace `SS_Key`; map static-entity record identifiers, which differ between environments; disable BPT triggers; create users and groups and retain the mappings; migrate application data **ordered by FK dependency**; migrate hybrid BPT instances; re-enable triggers; enable applications ([data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)). The gotchas are all identity gotchas. Nothing joins on names or ids across environments — only `SS_Key`. An auxiliary FKs-Map table recording source→destination id pairs is mandatory, cyclic dependencies need a two-pass insert, self-referencing keys need a post-insert update, and **soft keys are not mapped or replaced automatically the way foreign keys are**, which is the silent trap. Binary attributes are discoverable by filtering attribute type to `BinaryData` and must be planned separately. In cloud, permissions are limited to data-reader and data-writer, so triggers cannot be disabled and the documented workaround is to delete destination event rows first — the guide's own example being an unqualified `DELETE FROM OSEVT_ORDER` ([how-to-migrate-data](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/11-how-to-migrate-data.md)). The physical-name mapping lives in `OSSYS_ENTITY.Physical_Table_Name`; the default format is `OSUSR` plus a **hash of the eSpace name** (stable across environments, algorithm undocumented, so treat it as opaque), configurable via `Compiler.DefaultPhysicalTableName` in `OSSYS_PARAMETER` to a legacy `OSUSR_<ESPACE_ID>_ENTITYNAME` form or to a bare entity name — the last of which weakens security because the Hub Server can no longer runtime-check table access ([physical table name format](https://www.outsystems.com/forums/discussion/3444/configuring-the-physical-table-name-format-for-entities/)). Renaming an entity does not rename the table, so physical names can differ per environment and must never be hardcoded.

Two claims circulating in this area should be carried as unverified rather than upgraded. **A platform-wide row-level `Is_Active` soft-delete convention for business entities has no primary-source documentation** — the only sighting is on `OSSYS_User`-like system tables, and attribute-level `isActive = false` is a *schema*-level soft-delete of columns, not rows; "OutSystems soft-deletes your rows via Is_Active" appears to be a developer convention in many apps rather than platform behaviour. And **no primary source enumerates the complete list of OutSystems-managed columns on `OSUSR_*` tables** — the DDL exporter README explicitly declines to provide one and the official guides do not. That is a real gap for anyone writing an extractor. Multi-tenancy is similarly uncovered: `_TENANT_ID` appears on `OSEVT_*` rows and a tenant entry in the FKs-Map, but how `TENANT_ID` on multi-tenant business entities should project into a new schema is documented nowhere found.

On extensions, the picture is a one-bit question with large consequences. Opening a `.xif` in Integration Studio produces a folder with the extension's source code next to the `.xif` after one compile ([forum 85629](https://www.outsystems.com/forums/discussion/85629/programmatically-extract-source-code-from-xif/)), but **source is optional** — only binaries are needed for an extension to work, and OutSystems' own AWS connectors reportedly hide their implementation in a DLL ([forum 85074](https://www.outsystems.com/forums/discussion/85074/is-it-possible-to-access-c-code-of-an-extension/)). There is no Integration Studio CLI, so this cannot go in CI; the community workarounds proposed were GUI robots. The practical step is a one-time human sweep: for every `.xif` in the factory, does a source folder materialise on open? That boolean materially changes the estimate, because an extension with source is the best artifact in an exit (real, idiomatic .NET you can lift nearly verbatim) and one without is the worst.

## Legal: your own logic is on solid ground, the OML format is genuinely contested, and the losing claim is always breach of contract

**This is research, not legal advice.** A specific customer's signed Order or negotiated MSA may differ materially from the published standard-form terms and takes precedence for that customer; any organisation acting on this needs its own counsel reading its own executed contract. Several clause descriptions below are **close paraphrase rather than verbatim quotation** — the enumerated MSA §3.2(i)–(xi) restrictions, MSA §8.4, and 17 U.S.C. §1201(f)(1)–(4) — because the researcher's fetch tool capped excerpts at roughly 125 characters; they are not presented in quotation marks, and anyone relying on them must read the source.

The ownership split is clear and favourable. MSA §6 states verbatim that *"All Intellectual Property Rights in and to Applications and Customer Content are owned by Customer"*, with the mirror provision vesting the Software and Professional Services Tools in OutSystems ([MSA, updated 1 February 2026](https://www.outsystems.com/legal/master-subscription-agreement/)); EULA §4.2 says the same for Applications and End-User Content ([EULA, updated 8 July 2024](https://www.outsystems.com/legal/end-user-licensing-agreement/)). The restriction clause is drafted against "the Software," not against "Applications," and both the MSA and EULA reverse-engineering clauses are expressly qualified by the words except to the extent permitted by applicable law — the standard hook for mandatory statutory exceptions. On a plain reading, documenting your own business logic is not deriving source code from the Software.

**The contested point is the MSA §1 definition of "Software,"** which reads, verbatim, that Software includes *"components generated by OutSystems software products to facilitate the creation of Applications"*, *"including without limitation OutSystems Markup Language and low-code models"*, *"to the extent those components do not incorporate Customer Content"*. A real `.oml` for a working application plainly contains both halves — platform-generated model structure claimed as Software, and the customer's logic, entities, text, queries and assets as Customer Content and Application. **An `.oml` is therefore a hybrid object under these terms, not unambiguously yours.** No public OutSystems statement, FAQ or support article addressing whether customers may parse their own OML with third-party tools was found, in either direction.

That drafting tension produces a three-tier risk model, and the risk is not symmetric across activities. **Tier one, strongest position:** reading an `.oml` you own to extract your own logic, entities, screens and SQL. You own the Application; §6 says so; EU Art. 5(3) observation/study/testing covers inspecting your own lawfully-used program and, per *SAS Institute v World Programming* (CJEU C-406/10, 2012), licence terms purporting to restrict that exception are void. **Tier two, weakest of the model-layer activities:** reverse engineering the `.oml` container format itself and publishing a general-purpose OML parser or spec. That is directly characterisable as deriving the structure of something the MSA defines as Software, and if the parser is shipped as a migration product it also engages **MSA §3.2(v)**, which bars using the Software to provide third-party training or for the purpose of building or operating a competitive product. **Tier three, squarely prohibited:** decompiling Platform Server, Service Studio, Integration Studio, LifeTime, the Deployment Controller, licence-enforcement components or `OutSystems.*` runtime DLLs, subject only to narrow statutory exceptions. A corollary follows: where OML parsing and DLL decompilation yield the same information, **the OML route is the lower-risk one**, because the OML is a model you authored even if its format is contested, whereas the DLLs are artifacts of the vendor's compiler and runtime. One independent restriction deserves separate mention because it bites regardless of copyright: **§3.2(iv) bars circumventing access or usage-measurement controls**, which would also raise a US §1201(a) circumvention question — but the measurement above establishes that no technological protection measure stands between you and an `.oml`, so nothing needs circumventing.

The jurisdictional asymmetry is the single fact most worth checking before committing. In the EU and UK, **Directive 2009/24/EC renders contract terms contrary to the back-up, observation/study/testing and decompilation provisions null and void** (Recital 17 given effect in Art. 8, [consolidated text](https://www.legislation.gov.uk/eudr/2009/24/body/adopted?view=plain)), so there is a mandatory floor of rights OutSystems cannot contract away; and *SAS v WPL* held that **copyright protection does not extend to a program's functionality, programming language, or file format** ([CMS Law](https://cms.law/en/gbr/legal-updates/sas-v-wpl-who-dares-loses)), which is directly on point for understanding an `.oml` container. Article 6's conditions are nonetheless demanding: the acts must be indispensable for interoperability of an independently created program, the information must not have been previously readily available, and the acts must be confined to the parts necessary ([Art. 6](https://www.legislation.gov.uk/eudr/2009/24/article/6)), with Art. 6(2) barring use for a program substantially similar in its expression. In the US there is **no equivalent anti-override rule**: fair use and §1201(f) are defences to copyright and anti-circumvention claims, not to breach of contract. OutSystems maintains a [separate page on the contracting entity, governing law and jurisdiction](https://www.outsystems.com/legal/governing-law-jurisdiction), so a US-governed Order is meaningfully riskier than an EU-governed one for identical technical activity.

And here is the finding that should set project design. **Across every analogous dispute found, the vendor's winning claim was breach of contract, not copyright infringement.** In *IBM United Kingdom Ltd v LzLabs GmbH & Ors* [2025] EWHC 532 (TCC), handed down 10 March 2025, the court rejected the defendants' reliance on observation/study/testing and interoperability rights under the Software Directive, found Winsopia had breached its IBM Customer Agreement through large-scale disassembly, decompilation and translation over several years, held LzLabs and its principal liable for procuring those breaches, found an unlawful means conspiracy, and — this is the part worth surfacing prominently — **rejected reliance on the defendants' clean-room procedures**, describing them as ostensibly designed to maintain operational separation ([Brick Court Chambers](https://www.brickcourt.co.uk/news/detail/court-finds-conspiracy-to-reverse-engineer-ibm-mainframe-software); [full judgment](https://caselaw.nationalarchives.gov.uk/ewhc/tcc/2025/532)). Concealment also cost them their limitation defences. The same pattern recurs in *SAS v WPL*, where WPL won on EU copyright yet the Fourth Circuit affirmed its liability for breaching the licence agreement ([4th Cir. opinion](https://eff.org/files/2021/10/14/sas_v._wpl_ca4-opinion_10-24-2017.pdf)), in *IBM v Micro Focus* (filed November 2022, [The Register](https://www.theregister.com/2022/11/22/ibm_sues_micro_focus_for/)) and in *CA v ISI Software* (2010, over a migration tool, [Database Journal](https://www.databasejournal.com/database-news/ca-sues-software-developer-isi-software-over-db2-migration-tool/)). **No OutSystems litigation over reverse engineering or migration was found at all**, nor any against Mendix, Salesforce, ServiceNow or Appian — most likely market youth and quiet settlement rather than vendor tolerance. What distinguished every losing defendant from a legitimate internal migration is actionable: all built a commercial product competing with the licensor, all decompiled the vendor's own software at scale over years, all concealed it, and LzLabs used a licensee entity as a conduit for a non-licensee developer. A customer extracting its own application's logic from artifacts it owns, for its own internal migration, documented and disclosed, sits on the opposite side of every one of those factors. Procedural theatre is not a substitute for authorisation or genuine minimisation.

Finally, the exit right and the asymmetry it creates. **MSA §8.4(ii)** entitles the customer, on termination or expiry, to detach a copy of its Applications in source code format plus its Customer Content, subject to the Documentation's specifications and limitations — conditioned on **written notice of the Detachment request, payment of all remaining fees due, and completion within 30 days following the end of the applicable Subscription Term**, after which the Software must be de-installed or destroyed; EULA §6.2(ii) mirrors it. There is **no in-term export right, no source-code escrow, and no general data-portability clause** in the published MSA. The consequence is structural and is the practical core of the lock-in, independent of code quality: **you cannot detach to evaluate feasibility while still subscribed, so no team can test the quality of its own escape hatch before committing to terminate.** A team that wants source during the term must negotiate an in-term extraction right into the Order — and a renewal negotiation is the moment of leverage to do it, alongside a written acknowledgement that the customer may parse its own OML. Existence of the Detachment right cuts both ways: it supports a customer arguing that extracting its own application is within the spirit of the bargain, but it also weakens any later argument that decompilation was "necessary" because the information was not previously readily available. For ODC there is **no published detachment mechanism at all**; a forum answer states there is currently no equivalent public mechanism generating a traditional .NET solution package, and that ODC detachment would be a contractual arrangement ([forum 105782](https://www.outsystems.com/forums/discussion/105782/detachment-process-from-outsystems-odc-any-guidance-or-experience/)). ODC tenants should assume a weaker exit position than O11 tenants until OutSystems states otherwise in writing, and should get the ODC equivalent specified by the account team early. One unresolved question worth asking OutSystems directly: whether the detached package includes the OutSystems runtime DLLs, and on what licence terms after termination.

## morluto/rea is the wrong tool for this pipeline, with one conditional secondary lane

**Verdict: 0% fit for the `.oml` work, no softening.** [`morluto/rea`](https://github.com/morluto/rea) is not a library of agents. It is a single large TypeScript **MCP server plus CLI** (npm package `rea-agents`, version 6.7.0) fronting third-party binary-RE engines — Ghidra, Hopper, IDA, JEB, Rizin, Frida, objdump, gdb, apktool and others — in a provider-adapter pattern with an "Evidence" record as the common output ([README](https://raw.githubusercontent.com/morluto/rea/main/README.md)). The repo contains exactly **five skills**, four of which are internal maintainer skills; the "agents" in the name refers to the agents that call REA. A search across **all 5,076 blob paths** in `main` returned **zero hits for `outsystems`, `mendix`, `lowcode`/`low-code`, `powerapps` and `salesforce`**; the four `oml` hits are coincidental substrings in test filenames and a `wrangler.toml`, and the two `espace` hits are the substring inside "namespace" ([recursive tree API](https://api.github.com/repos/morluto/rea/git/trees/main?recursive=1)). The README's target table covers 28 target classes and **none is a model file, metadata repository or low-code package**. Most tellingly, the tool rules itself out: the main skill's own description says to **skip REA for ordinary source-repository architecture analysis**, and the body repeats that for ordinary analysis of a complete source repository you should use normal repository tools and not run REA readiness or provider commands ([SKILL.md](https://raw.githubusercontent.com/morluto/rea/main/.agents/skills/reverse-engineer-anything/SKILL.md)). It will also refuse an `.oml` by design — inputs without admitted CLI metadata do not become managed assemblies through naming or routing guesses. Do not architect the main `.oml` → spec → code pipeline on it.

The conditional value is a **secondary evidence lane for deployed artifacts**, and it is cheap to evaluate because the relevant paths need only Node 22+ and no commercial decompiler. REA's managed-code surface is exactly **seven static tools** — `inspect_managed_artifact`, `inspect_managed_members`, `inspect_managed_native_boundaries`, `compare_managed_members`, `verify_managed_native_boundaries`, `import_managed_reconstruction`, `project_managed_application_graph`, each with a matching CLI command — which inspect .NET PE/CLI artifacts **without loading or executing their code**, returning paged `types`, `exported_types`, `fields`, `methods`, `member_refs`, `call_edges`, `field_accesses` and `user_strings` ([docs/managed-code-analysis.md](https://raw.githubusercontent.com/morluto/rea/main/docs/managed-code-analysis.md)). Alongside that, `analyze_javascript_application` returns modules, imports, source maps, routes and IPC relationships, and HAR/SAZ capture analysis gives requests, responses and exposed payloads — which maps onto an OutSystems front-end bundle and its generated screen-data endpoints. **But the mapping from those capabilities to OutSystems artifacts was the researcher's own inference, explicitly not verified against the repo**, which has no OutSystems content whatsoever, and no public report or case study of anyone pointing REA at an OutSystems artifact was found. **Run `rea inspect-managed-artifact` against a real OutSystems-generated DLL and `rea analyze-javascript-application` against a real front-end bundle before any plan depends on it.** Note too that this lane only exists where you hold binaries — and per the previous section, on a self-managed Platform Server you hold the `.cs` source instead, so the lane's realistic scope is front-end-only footholds and copied `running\` folders.

Metadata snapshot from the GitHub REST API on 2026-10-21: MIT-licensed, created 2026-04-14, pushed the same day as the check, **354,982 stars / 89,162 forks**, 1,257 watchers, 1,684 open issues and PRs, 93,350 KB, 1,925 `*.test.ts` files, Stryker mutation testing, 1,848 merged PRs and 1,646 closed issues in roughly six months ([GitHub API](https://api.github.com/repos/morluto/rea)). **Flag the star figure as surprising and contested**: 355k stars in six months is extraordinary, aggregators disagree sharply — one reported 234,477 stars and 58,512 forks as of 14 October, OSS Insight listed 7,355 forks ([aitoolly](https://aitoolly.com/de/ai-news/article/2026-10-15-rea-emerges-on-github-trending-to-enable-ai-agents-to-reverse-engineer-software-and-native-binaries); [ossinsight](https://ossinsight.io/analyze/morluto/rea)) — and the count could not be independently audited for inorganic growth. Contribution is heavily concentrated in one maintainer (2,104 commits against 592 and 524 for the next two). Operational cautions, all drawn from the project's own documentation: **pin `rea-agents@6.7.0` rather than `@latest`** (6.3.0→6.7.0 shipped in nine days, and the skill acknowledges that docs on `main` may describe capabilities absent from an older npm release); **`setup` mutates your agent's MCP configuration and replaces the bundled skill**, so review the plan with `--dry-run --json` and prefer CLI-only invocation; **runtime-capture tools run or interact with the target using your user permissions**, so stay on the static paths; keep targets in an isolated directory; and heed the README's own **typosquat warning** that a similar repository name or copied README does not establish that a download is official.

For the stage that actually matters — turning a readable representation into a specification — **[`sandeco/reversa`](https://github.com/sandeco/reversa) is the better-fitting complement.** It genuinely is a library of agents: it installs into `.agents/skills/` (and `.claude/skills/` for Claude Code), organises agents into eleven specialised teams, and exposes orchestrators including `/reversa` (a five-phase discovery pipeline), `/reversa-forward`, `/reversa-migrate` ("turn legacy specs into a rebuild plan for a modern stack") and `/reversa-docs`; the installer only creates new files and never modifies or deletes existing ones, agent writes are restricted to `.reversa/` and `_reversa_sdd/`, and it requests no API keys ([README](https://raw.githubusercontent.com/sandeco/reversa/main/README.md)). It is MIT, 1,783 stars, created 2026-04-26, last pushed 2026-10-21, and is backed by a paper ([arXiv 2605.18684](https://arxiv.org/abs/2605.18684)). The caveat is decisive for sequencing: **Reversa assumes a readable source tree**, and its README mentions no OutSystems or low-code support either. So `.oml` → readable representation is prerequisite work either way, and the two tools are complementary rather than competing — REA explicitly declines source-repository analysis, which is precisely Reversa's domain. The most transferable idea in REA, independent of adoption, is its **Evidence abstraction**: every result carries its provenance, coverage, unknowns and limitations, keyed by `evidence_id` and artifact SHA-256. Build that into any OutSystems extraction pipeline regardless of what tooling you choose.

## A staged plan for someone starting from a single .oap in a git repo

Ordered by cost-to-value, with the solved, the hard and the closed kept strictly separate.

**Stage 0 — free, today, no OutSystems software (hours).** `unzip` the `.oap`, parse `Manifest.xml` with any XML library. You get the module inventory, the eSpace reference and dependency graph, `ApplicationKind`, theme colour, origin environment, the schema and server version stamps, the stable UIDs and the app icon. Fingerprint OutSystems packs on the ZIP comment `The Solution Pack Manifest` and discriminate `.oap` from `.osp` on `IsApplicationPack`. **Solved.**

**Stage 1 — roughly twenty lines of Python, fully verified (hours).** Read the `OML` magic, the uint32 LE header length at `0x03`, slice the plaintext header, `zlib.decompressobj(-15)` the remainder, walk the fragment directory, split the Fast Infoset bodies. Two engineering notes from the measurement: **dispatch on the header version triple and fail loudly on unknown revisions** — `kelter-antunes/oml-utilities` embedding `OutSystems.Common.11.0.520.0` with an `UnsupportedNewerVersion` path against a file produced by platform `11.55.93.65333` is the documented failure mode — and do not hardcode the directory offset at 1,492; **scan offsets 0 to ~8192 for the longest self-consistent directory whose declared lengths sum exactly to `len(blob) − dir_end` and every one of whose bodies starts `E0 00 00 01`.** That test is unambiguous. A `strings` pass over the fragments already yields action names, structures, variables and settings for free. **Solved.**

**Stage 2 — the data model, the most solved leg of the whole problem (days).** Follow the [`danielbdyer/outsystems-ddl-exporter`](https://github.com/danielbdyer/outsystems-ddl-exporter) pattern: one-shot Advanced SQL over `OSSYS_ENTITY` and `ossys_Entity_Attr` into parseable JSON, then **profile the live database** for physical nullability, uniqueness, foreign keys and data reality — NULLs, duplicates, orphans — rather than trusting declared metadata, and emit one `CREATE TABLE` per entity. Two findings make the profiling step non-optional: OutSystems' logical references are frequently **not enforced in the physical database** (constraints only materialise when `sys.foreign_keys` confirms them), and the FK-Map plus dependency-ordered insert pattern that OutSystems documents for environment-to-environment migration is exactly what an exit needs with your new schema as the destination. Teams who skip it and attempt a straight bulk copy will corrupt referential integrity, because OutSystems identifiers are environment-local autonumbers. Note the exporter has **no LICENSE file** — treat it as a pattern to reimplement, not a dependency to adopt. Also note the platform **blocks Advanced SQL referencing `OSSYS` or `OSUSR` prefixes** ([forum 23212](https://www.outsystems.com/forums/discussion/23212/how-i-get-the-outsystems-data-schema/)), so plan the access route. **Solved, with caveats.**

**Stage 3 — supported logic extraction, and the one thing worth building (weeks).** Install Service Studio 11.55.91+, start the MCP server from `Edit > MCP Configuration...`, drive the GA read tools over `http://127.0.0.1:41820/mcp`, and investigate `getSerializedObject*` as the backbone of bulk structural export. Use this interactive channel to **write and validate your IR specification against ground truth**, then — and only then — build the one genuine gap: **headless batch extraction**, either by orchestrating Service Studio or by referencing `OutSystems.Model.V1.dll` from your own .NET 8 process in the `oml-cli` style. Validate your Stage 1 clean-room parser against Stage 3 output on the same module; disagreements between the two are exactly where a migration's bugs hide. For portfolio scale, layer LifeTime API v2 (via [`outsystems-pipeline`](https://github.com/OutSystems/outsystems-pipeline), pulling `swagger.json` from the live instance for the exact contract) for inventory and the Code Quality API for prioritisation, and use LifeTime v2's `.oap` operations for sanctioned artifact acquisition. Call the Platform Documentation API directly — [OutDoc](https://www.outsystems.com/forge/component-overview/159/outdoc-o11) is its open implementation — rather than scraping OutDoc's output. **Buildable; this is where the engineering budget goes.**

**Stage 4 — genuinely hard, scope explicitly (months, uncertain).** Fast Infoset to a faithful XML tree needs a real decoder and no published source documents the OutSystems FI vocabulary per model version, so it must be induced empirically and re-induced per platform release. `ParsedExpression` ASTs with type-by-key references must be re-serialized into readable expression text, which is the hardest named target in the format and should carry its own line in a plan. UI layout fidelity is unsolved by everyone — ACACIA concedes layout cannot be exported, OutSystems tells you to rebuild rather than convert when UX changes, and the one academic study found UI the most prioritised feature and the major bottleneck before its author abandoned the project ([Romão 2021, UNL](https://run.unl.pt/bitstream/10362/130408/1/Romao_2021.pdf)). Round-trip repacking is untested and likely blocked by the `Signature` fragment and the per-object `GeneralHash`/`DebuggerHash`.

**Closed, do not plan around it.** ODC as a reverse-engineering source: no modules, no `.oap` export, no per-module model API, no packaging spec, no detach process, and Aurora PostgreSQL under the data layer. In-term contractual export: MSA §8.4(ii) runs for 30 days *after* the subscription term ends, so it cannot function as a migration tool. Decompiling OutSystems platform runtime DLLs: contractually prohibited and only narrowly excused by statute.

**Two decision gates worth setting before any code.** First, legal and procurement: identify the contracting OutSystems entity and governing law, because the EU/UK mandatory-exceptions floor versus the US no-anti-override position changes the risk profile of identical technical activity; ask OutSystems in writing for Detachment scope, whether runtime DLLs are included and on what terms, and the ODC equivalent — written vendor consent removes the contractual question entirely, which is where the actual litigation risk lives, and there is no downside to asking. Second, keep the toolkit internal and non-distributable: publishing a general-purpose OML parser is the step that converts a §117/Art. 5(3) story into an LzLabs/§3.2(v) story, and project naming, README language and commit messages will be read as evidence if a dispute ever arises.

## Conclusion

The research inverts the question that teams usually ask. The hard part of getting out of OutSystems was never the file format — that is decoded, unencrypted, and now reproducible from a twenty-line script — and it is no longer access to the model, because OutSystems itself shipped a GA read API in 2026 that is strictly more capable than any community parser. The hard part is **semantics**: `ParsedExpression` ASTs, aggregate-to-SQL fidelity, and UI layout, none of which any tool, open or commercial, claims to recover faithfully, and none of which has a single published accuracy number attached to it. The most useful reframing is that **extraction is now cheap enough to be an estimation instrument rather than a commitment**: Stages 0 through 2 cost days, require no vendor involvement, and produce an auditable capability inventory — screen counts, action counts, expression counts, entity counts with real physical nullability — which is precisely what nobody can buy, because no public per-screen effort figure exists. Run the inventory first and derive your own effort model from your own factory; any vendor quote that does not rest on one of those is a guess with a price attached.

Two asymmetries deserve to outlive this report. **Technically**, the direction of travel favours staying: OutSystems opened the model to AI agents *inside* the platform boundary and markets it as evolving in place with no migration and no replatform, while shipping an assessment tool and not a conversion tool for its own O11→ODC path — and ODC, the destination it is steering customers toward, closes nearly every extraction route O11 leaves open. The irony is that the same MCP server pitched as a retention tool is the best-supported model-extraction channel OutSystems has ever shipped, and nothing in its terms appears to restrict what you do with what you read. **Contractually**, the exit right is real but structured so it cannot be rehearsed: detachment is available only for thirty days after you have already committed to terminate. The one decision available today that changes that is not technical at all — it is negotiating an in-term extraction right into the Order at the next renewal, when leverage exists. Everything else in this report is a question of engineering budget; that one is a question of timing, and the window closes on someone else's schedule.
