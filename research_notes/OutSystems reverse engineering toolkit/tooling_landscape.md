# OutSystems Reverse-Engineering Tooling Landscape (open-source, Forge, official, commercial) — state as of Oct 2026

Scope note on dates: GitHub figures below are from the GitHub API on 2026-10-21. `pushed` = last commit push date (the reliable staleness signal); GitHub's `updatedAt` field often moves for non-code events, so where the two disagree I use `pushed`.

## Q1 — Open-source / GitHub: what repos exist for OutSystems extraction, OML parsing, metadata dumping, documentation generation, or migration?

### Takeaway
The open-source layer is thin and mostly built by individuals: exactly one maintained-ish OML-to-XML converter (`oml-utilities`, last commit Feb 2023), one actively-developed metadata/DDL extraction pipeline (`outsystems-ddl-exporter`, 0 stars, F#, commits through Oct 2026), and — the big 2026 change — two *official* OutSystems MCP repos that expose the O11 application model to coding agents. No open-source project generates application code from an OML.

### Cited Findings

**OML file access**
- `silviogarbes/oml-utilities` — MIT, console app, 4 stars, **last commit 2023-02-09** (effectively unmaintained). The single most important OSS primitive: `oml manipulate "<in>" "<out>" --format xml` "generates a XML file in the `OutputFilePath` destination containing all fragments" — i.e. a full OML→XML dump. Also `oml show-headers` (returns `[Writable|ReadOnly],[DataType],[HeaderName]:[HeaderValue]`, values may be URL-encoded, e.g. `ESpaceType`), `oml manipulate -H "Name:Value"` (header rewrite), `oml manipulate -F "<eSpaceFragment FragmentName=...>"` (full fragment replacement — "enables advanced use cases by allowing to programatically modify the code [of] an OML file"), `oml text-search "<dir>" "<keyword>"` (case-sensitive text search across a directory of OMLs, "Ideal for find uses of Built-function"), and `oml show-platform-versions [--full-version] [--latest]` which "Lists the supported platform versions of the utility" as labels like `O10` or full versions like `9.1.603.0` — so OML format support is version-pinned and the tool only knows versions up to its 2023 build — [repo](https://github.com/silviogarbes/oml-utilities)
- Forks, both low-signal: `kelter-antunes/oml-utilities` (C#, 0 stars, last commit 2024-06-11) and `kelter-antunes/oml-utilities-library` (0 stars, last commit 2024-12-20, **no README, no license**) — [fork](https://github.com/kelter-antunes/oml-utilities); [library fork](https://github.com/kelter-antunes/oml-utilities-library)
- `achinita/ImportResources` — C#, 3 stars, last commit 2024-07-12. "A small tool that allows to import full folders of resources into OML files, using ServiceStudio.exe." Evidence that driving `ServiceStudio.exe` programmatically is a viable automation surface — [repo](https://github.com/achinita/ImportResources)

**Metadata / DB extraction**
- `danielbdyer/outsystems-ddl-exporter` — F#/.NET, **0 stars, no LICENSE file, but actively committed (last push 2026-10-21)**. The most substantial extraction pipeline found. Its README states it: "Extracts OutSystems' logical data model (via one-shot **Advanced SQL**) into a **parseable JSON** payload"; "**Profiles** the live SQL Server for physical nullability, uniqueness, FKs, and data reality (NULLs, duplicates, orphans)"; applies "policy-driven tightening (evidence-gated `NOT NULL`, UNIQUE, and FK creation)"; builds "**SMO** object graphs (no regex/string-concat), then **emits one CREATE TABLE script per entity** (indexed by module) with inline defaults, foreign keys, indexes, and `MS_Description` extended properties"; and "Optionally **compares** your intended model against a **DMM-produced DDL** to ensure **1:1 parity**" before SSDT ingestion. Ships CLI verbs `extract-model` and `build-ssdt` (`dotnet run --project src/Osm.Cli`), plus `src/AdvancedSql/outsystems_model_export.sql`, `src/AdvancedSql/outsystems_metadata_rowsets.sql`, and `notes/outsystems-metadata-research.md` — [repo](https://github.com/danielbdyer/outsystems-ddl-exporter)
- A GitHub code search for `OSSYS_ENTITY_ATTR` (2026-10-21) returned essentially only: OutSystems' own docs repos (`docs-howtos`, `docs-support`, `docs-odc`), `danielbdyer/outsystems-ddl-exporter`, and a Chinese translation of an itnext blog post. There is no community library for the OutSystems metamodel — [search performed via `gh search code`]; the itnext source: [OutSystems server-side data model](https://itnext.io/)
- `kelter-antunes/outsystems-eSpace-meta-model` — 1 star, **last commit 2022-12-30, abandoned, no license, no README**; repo contains only a `DocumentationAPI` folder — [repo](https://github.com/kelter-antunes/outsystems-eSpace-meta-model)

**Official OutSystems repos (new in 2025–26, the most important development)**
- `OutSystems/outsystems11-mcp` — C#, MIT, 23 stars, last commit 2026-10-13. Distributes the skill for a **local MCP server embedded in Service Studio 11.55.91+**, reading/writing "Your O11 application model, read and written via the OutSystems Model API". Read is **Generally Available**: "Every read tool — `getDataModel`, `getScreen`, `getServerAction`, `runQuery`, `getValidationMessages`, `listApps`, …". Write is **Beta**: "`applyModelApiCode` lambdas (new or changed entities, screens, actions, …), plus `omlMerge`, `omlReset`, `omlRefreshReferences` and `omlPublish`". Stated use cases include "**Generate documentation** — onboarding guides and process flows for the module open in Service Studio", "**Map dependencies**", "**Surface risk**", and "find dead code and gaps in test coverage". Operationally: the server "does **not** start automatically — you start it per session", via `Edit > MCP Configuration...`, default port `41820`, registered with `claude mcp add --transport http servicestudio http://127.0.0.1:41820/mcp --scope user`. Runs locally "including on-premises and air-gapped deployments. Nothing leaves your environment." Supported agents: Claude Code (optimized), GitHub Copilot CLI/VS Code, Google Antigravity, Kiro, Cursor, Codex CLI — [repo](https://github.com/OutSystems/outsystems11-mcp)
- `OutSystems/outsystems-mcp` — Python, MIT, 41 stars, last commit 2026-10-21. A **different, remote** MCP: "the OutSystems endpoint at `https://<my-tenant>/mcp`, which exposes the tools and signs you in to your tenant. OutSystems hosts it and updates it on the tenant side". Skill rules are tenant-lifecycle oriented ("confirm before changing tenant state, poll long-running operations until they finish, decide retries from the error category, prefer the asset key over names"). Note the repo documents that Claude Desktop's native custom-connector OAuth "always fails against any OutSystems tenant today" and pins `mcp-remote@0.14.3` because "releases 0.9.0 through 0.13.5 fail every sign-in with `IssuerMismatchError`" — [repo](https://github.com/OutSystems/outsystems-mcp)
- `OutSystems/outsystems-pipeline` — Python, Apache-2.0, 51 stars, last commit 2026-10-07. "Python package and pipeline examples to accelerate the integration of OutSystems with third-party CI/CD tools" — the maintained wrapper around LifeTime APIs (useful for enumerating applications/modules/environments as a pipeline step) — [repo](https://github.com/OutSystems/outsystems-pipeline)
- `OutSystems/techsupp-osdiagtool` — C#, 12 stars, last commit 2026-06-17, "OutSystems Support Diagnostics Tool" — collects platform/environment diagnostics — [repo](https://github.com/OutSystems/techsupp-osdiagtool)
- `OutSystems/LifetimeServicesExample` — Java, 3 stars, last commit 2025-02-16, "samples on how to use the OutSystems Platform LifeTime Services API" — [repo](https://github.com/OutSystems/LifetimeServicesExample)

**Unofficial CLI**
- `tony4outsystems/odc-cli` — **Rust, 0 stars, no license declared**, last commit 2026-10-01. "CLI (`odc`) for driving the OutSystems Developer Cloud (ODC) APIs described in `api-specs/`." Commands seen: `odc login <tenant-url> <client-id>`, `odc discover`, `odc latest-revision --asset`, `odc deploy <asset> <env>`, plus `validate`. Auth via ODC Portal **Management > API Clients** (`ODC_TENANT_URL`/`ODC_CLIENT_ID`/`ODC_CLIENT_SECRET`, stored plaintext in `~/.odc/config.json` at 0600). Distributed via `brew install tony4outsystems/tap/odc-cli` and GitHub Releases (prebuilt binaries, SHA-256 `checksums.txt`). Ships a Claude Code skill at `skills/odc-cli-helper` that "teaches Claude how to install, configure, and drive the `odc` CLI". **Deployment/lifecycle oriented — not an extraction tool** — [repo](https://github.com/tony4outsystems/odc-cli); [homebrew tap](https://github.com/tony4outsystems/homebrew-tap)

**Abandoned / dead ends (flagged explicitly)**
- `5O4R3S/OutSystems-Scan` — Python, MIT, 26 stars, **ARCHIVED, last commit 2025-03-31**. README headline: "# OutSystems-Scan (Outdated)" and "ATTENTION: This tool is outdated and discontinued, I made a new WEB version". The replacement "WEB version" is not open source and no URL for it is given in the repo — [repo](https://github.com/5O4R3S/OutSystems-Scan)
- `kypseli/outsystems-lifetime-deploy` — PowerShell, 0 stars, **last commit 2018-11-05, abandoned** — [repo](https://github.com/kypseli/outsystems-lifetime-deploy)
- `Mjelkic/outsystems-migration-tool` — JavaScript, 0 stars, last commit 2026-04-10, **no description and no README surfaced** — unknown/probably personal scratch — [repo](https://github.com/Mjelkic/outsystems-migration-tool)
- `proccyboy72/outsystems-migration-assessment` — 0 stars, last commit 2025-06-19, **no description** — [repo](https://github.com/proccyboy72/outsystems-migration-assessment)
- Name collisions to avoid: `dxrcy/oml-rs` (Rust, 2024-01-29), `nikso-itu/duckdb-oml` (2023-11-07), `iot-lab/oml-plot-tools`, and `praskov/Ksync` (OtsAV DJ playlists) all handle *different* file formats also called "OML" and are irrelevant.
- Adjacent: `madharjan/outsystems-docs` — "Semantic Search on OutSystems ODC & O11 Documentation using MCP" — docs retrieval, not model extraction — [repo](https://github.com/madharjan/outsystems-docs)

### Inferences
- The practical OSS extraction stack is a two-path split: **OML-file path** (`oml-utilities` → raw eSpace XML, then you write your own parser against an undocumented schema) versus **runtime-metadata path** (Advanced SQL against the OSSYS metamodel → JSON, per `outsystems-ddl-exporter`). Neither path alone yields logic; only the OML XML contains action flows and screen trees.
- `oml-utilities`' explicit `show-platform-versions` list implies the OML container format changes per platform release and that a 2023-vintage tool may fail or silently mis-parse OMLs saved by 2026 Service Studio builds. This is the single biggest technical risk in an OML-file-based pipeline.
- The MCP route is strictly more capable than file parsing for *logic* (it reads the live model through a supported API rather than guessing at XML), but strictly less capable for *batch* work: it reads "the module open in Service Studio", one module at a time, on a Windows desktop, with a manually started server. It is an interactive tool wearing an API's clothes.
- Nobody has published an open-source OML→code generator. Every code-generation claim found is commercial and closed.

### Gaps
- The OML XML schema itself is undocumented publicly; I found no published schema, grammar, or element reference for eSpace fragments. `oml-utilities` tells you how to get the XML but nothing about what is inside it.
- Could not determine whether `oml-utilities` depends on shipped OutSystems DLLs (which would make it license-encumbered and Windows-only) — the repo tree listing call failed and I did not open the source files.
- `Mjelkic/outsystems-migration-tool` and `proccyboy72/outsystems-migration-assessment` contents unexamined — both are 0-star, undescribed repos, likely noise.
- No OSS project found that targets **ODC** model extraction at all; everything above is O11/eSpace-era.

## Q2 — OutSystems Forge components

### Takeaway
Forge gives you three things worth having — **OutDoc** (the only real documentation generator, and the open implementation of the Platform Documentation API), **Discovery** (dependency/architecture analysis, but stale and with no documented export), and the **AI Mentor Studio API** (programmatic technical-debt findings) — all O11-only, all BSD-3 or similar, and none of them emit anything resembling source code.

### Cited Findings
- **OutDoc (O11)** — stable **8.0.13**, **BSD-3**, listed as "Supported" by OutSystems, compatible with OutSystems 11, rated 4.6 from 56 ratings. "Automatically generates documentation for eSpaces and Solutions, including data model, reference/dependency, and process diagrams, plus details on processes, screens, actions, database, and images. It is an open implementation of the Platform Documentation API." Hard constraint on the page: "This component is only available for the .NET stack of the OutSystems Platform." Still maintained — the page showed an upload date of 12 Oct described as "5 days ago" when fetched on 2026-10-17/21, and 8.0.13 release notes fix an "Object reference not set to an instance of an object" error when generating module documentation and "Client Variables inside folders being missing from generated documentation" — [Forge page](https://www.outsystems.com/forge/component-overview/159/outdoc-o11)
- Practitioner caveat on OutDoc: it "can generate the base version of your technical specs document", but "you may need to develop additional tools or features to manipulate and exhibit this information structured in the way required" — [OSQuay](https://www.osquay.com/knowledge-center/big-projects-generate-project-documentation-in-outsystems)
- **Discovery (O11)** — stable **6.0.3**, **BSD-3**, published by the OutSystems "Architecture Team", page shows upload date **01 September 2023** (older versions exist for OutSystems 10 and earlier). "A visual tool for analyzing and measuring factory architecture", features: "tracking architecture indicators, showing findings over time, validating dependency rules, and finding element consumers". The page **does not mention any export feature** — [Forge page](https://www.outsystems.com/forge/component-overview/409/discovery-o11)
- **AI Mentor Studio API (O11)** — Forge component exposing technical-debt data. Purpose per OutSystems: "Integrate technical debt data from AI Mentor Studio with other technical debt and BI tools you already use; Use technical debt data as a quality gate of an automated CI/CD pipeline." Recent releases: v1.34 added a v2 of `TechnicalDebt_Team` taking a team `Key` "to match the LifeTime API v2 format"; v1.33 "Optimized the way how the API retrieves the latest technical debt information"; v1.32 made `TechnicalDebt_Application` "return an error when the provided offset exceeds the number of available records" and fixed an understated `TotalResults` — [Forge page](https://www.outsystems.com/forge/component-overview/17621/ai-mentor-studio-api-o11); [release notes](https://success.outsystems.com/support/release_notes/ai_mentor_studio/)
- Known API limitation (community, ~900–1000 days old at time of writing, so possibly stale): "Using the API I can get Patterns GUID, Name, Category and Findings Count but I cannot find the weight associated with a pattern", and a later thread: "currently there is no way so that we can get tech debt % by weight from AI mentor studio API" — [forum 1](https://www.outsystems.com/forums/discussion/90612/get-pattern-weight-or-technical-debt-using-ai-mentor-studio-api/); [forum 2](https://www.outsystems.com/forums/discussion/95863/is-there-a-way-to-calculate-the-technical-debt-through-the-ai-mentor-studio-api/)
- **Factory Configuration (O11)** — stable **11.3.1**, OutSystems 11. "Lets you change the configuration of the components in a Service Center Factory" — default proxy for web references, custom handlers, Java integrated authentication, HttpRuntime parameters. "Not supported in Personal or Trial environments." A moderator notes "the module is now protected, so if changes are needed, the module should be cloned." **This is a factory *configuration* tool, not a reverse-engineering tool** — commonly mis-cited as one — [Forge page](https://www.outsystems.com/forge/component-overview/25/factory-configuration-o11)
- **DOC Assist (O11)** — narrower documentation helper: "documents site properties, processes, and timers", and "the capability to export the gathered data into Excel is its main feature" — [Forge page](https://www.outsystems.com/forge/component-overview/17661/doc-assist-o11)
- **"Migration as a Service"** — a Forge component exists under this name; I did not verify its contents, vendor, version or platform support — [Forge page](https://www.outsystems.com/forge/component-overview/9163/migration-as-a-service)
- The **O11 to ODC Conversion Assessment Tool** is itself distributed through Forge: "It is installed from Forge onto your O11 infrastructure and analyzes your application portfolio" — [product update](https://www.outsystems.com/product-updates/o11-to-odc-conversion-assessment-tool)

### Inferences
- OutDoc being "an open implementation of the Platform Documentation API" is the key fact for a build decision: the *API* is the asset, OutDoc is one renderer over it. A reverse-engineering pipeline should call the Documentation API directly and emit structured JSON/Markdown rather than scrape OutDoc's HTML/Word output.
- Discovery at a Sep-2023 upload date against a platform still shipping Service Studio 11.55.x in late 2026 suggests low-priority maintenance; and with no export, its value to a pipeline is a human-readable second opinion on dependencies, not machine input. Its dependency data lives in its own OutSystems entities, which you could query directly — but that is unsupported reverse-engineering of a Forge component.
- The AI Mentor Studio API gives *findings* (counts by pattern/category/app/team) but, per the forum threads, not the weights behind the score — so it is usable as a prioritization signal and quality gate, not as a reproducible debt metric.

### Gaps
- **No Forge component named "OMLResource" was found.** Searches for it returned only Factory Configuration and unrelated (Minecraft/JBoss) Forge results. If the asset exists it is not discoverable by that name; treat the name as unconfirmed.
- **No Forge component named "Service Studio Tools" was found.**
- No ODC-compatible version of OutDoc or Discovery surfaced. A documentation/dependency-analysis gap for ODC appears real but I could not positively confirm absence.
- Download counts for OutDoc/Discovery are not shown on the Forge pages, so relative adoption is unmeasurable.
- The "Migration as a Service" Forge component is unexamined.

## Q3 — OutSystems official tooling: what analysis output can it produce, and can it be exported?

### Takeaway
Official tooling is strong at *assessment* and newly strong at *agent-readable model access* (the Service Studio MCP), but every official "conversion" path targets another OutSystems runtime (Traditional Web→Reactive, O11→ODC) — not an exit to general-purpose source code. Exportability is best via the AI Mentor Studio API, LifeTime APIs, the Platform Documentation API, and the OSSYS metamodel.

### Cited Findings
- **Service Studio MCP / Model API** (see Q1 for tool names): read capabilities GA, writes beta and "staged and reviewed through Service Studio's interactive Compare-and-Merge window before anything is accepted into your module". OutSystems positions it explicitly as an *alternative to migration*: "modernize it with confidence… so you get AI speed without the cost, disruption, or risk of a replatform" and "**Evolve in place** — no migration, no replatform" — [outsystems11-mcp](https://github.com/OutSystems/outsystems11-mcp). Independent confirmation that this is the Model API's public surface: the Model API's own reference documentation did not surface in search, so these details rest on the OutSystems-owned repo.
- **O11 to ODC Conversion Assessment Tool** — GA **November 2025**, the first part of the O11→ODC App Conversion Kit. It "flags code, data, and infrastructure patterns that won't carry over to ODC, and gives clear guidance on how and where to fix incompatibilities", including "SQL queries and database constructs that will not work against Amazon Aurora PostgreSQL" (ODC's DB engine) — [product update](https://www.outsystems.com/product-updates/o11-to-odc-conversion-assessment-tool); [docs](https://success.outsystems.com/documentation/11/outsystems_11_to_odc_conversion/)
- **O11→ODC code conversion tool** — what is automated: running conversion for apps in a conversion plan, Finished / "Finished with errors" status per run, and listing the apps and modules with revision numbers included. What stays **manual**: verifying every asset is "Ready for ODC" or "Change in ODC" first; then "downloading each file, adjusting the converted code, checking for dependency updates, and fixing TrueChange errors"; publishing each app/library in ODC Studio "in producer-to-consumer order"; releasing libraries; reviewing converted app configurations. Output artifacts are "converted ODC apps and libraries, which are initially Unpublished and downloadable for editing in ODC Studio" — the page does not mention OML files or conversion reports — [docs](https://success.outsystems.com/documentation/11/outsystems_11_to_odc_conversion/execute_app_conversion/convert_code/code_conversion_using_the_tool/)
- Third-party read on the automation ceiling: OutSystems "is still developing automation to handle some of the conversion itself", with the summary that "assessment is automated while conversion largely is not"; and the assessment tool "does not tell you how long fixing it will take in your codebase with your team" — [Betty Blocks](https://bettyblocks.com/blog/outsystems-11-to-odc-migration-cost) (**note: Betty Blocks is a competing low-code vendor — competitive content, treat directionally**). A conflicting claim that the tool "outputs a readiness score and estimated migration effort" appears at [RapidDevelopers](https://www.rapidevelopers.com/outsystems-tutorial/outsystems-o11-vs-odc) and could not be verified against OutSystems documentation — prefer the official page.
- **Traditional Web → Reactive conversion accelerator**, built into Service Studio, "works on a clone so the original stays untouched"; official guidance adds that "If your migration strategy involves a significant UX redesign or architectural overhaul, consider building a new Reactive Web App from scratch rather than converting" — [docs](https://success.outsystems.com/Support/Enterprise_Customers/Upgrading/Introduction_to_migrating_Traditional_Web_to_Reactive_Web_Apps/Suggested_stages_of_Traditional_to_Reactive_App_migration). Practitioner view: "most of the code is not compatible between versions, and the migration requires extensive code refactoring, resulting in significant costs" — [Mediaweb](https://medium.com/mediaweb-creations/migration-from-traditional-web-to-reactive-odc-f9906e604345)
- **OSSYS metamodel** (the exportable, queryable description of the factory): `OSSYS_APPLICATION` → `OSSYS_APP_DEFINITION_MODULE` → `OSSYS_MODULE`, where modules are either eSpaces (`OSSYS_ESPACE`) or extensions (`OSSYS_EXTENSION`); `OSSYS_MODULE` is marked "for internal use only". Logical-entity→physical-table mapping lives in `OSSYS_ENTITY`; attribute metadata in `OSSYS_ENTITY_ATTR` — [OutSystems Platform Metamodel](https://success.outsystems.com/documentation/how_to_guides/data/data_migration_from_production_to_non_production_environment/outsystems_platform_metamodel/); [Factory Application Modules](https://success.outsystems.com/documentation/how_to_guides/data/data_migration_from_production_to_non_production_environment/factory_application_modules/)
- Access restrictions on the metamodel: OutSystems docs warn that DDL statements "could make the metamodel inconsistent, leading to misbehavior", so queries "should not go directly to the metamodel's physical tables"; a forum answer reports the platform **blocks Advanced SQL that references `OSSYS` or `OSUSR` prefixes**, with workarounds described. A practitioner adds that several of these entities are "undocumented and not recommended for use by OutSystems" and "should only ever be read, never written" — [forum](https://www.outsystems.com/forums/discussion/23212/how-i-get-the-outsystems-data-schema/); [Rutabaga Technology](https://www.rutabagatechnology.net/outsystems-aos-keeping-costs-under-control-with-automation/)
- **LifeTime API v2** is the supported programmatic inventory surface (applications, modules, environments, teams); the AI Mentor Studio API v1.34 change aligning on team `Key` "to match the LifeTime API v2 format" confirms both are current and interoperable — [AI Mentor Studio release notes](https://success.outsystems.com/support/release_notes/ai_mentor_studio/); [LifeTime API samples](https://github.com/OutSystems/LifetimeServicesExample)
- Other official CLIs, none of which extract application logic: **Configuration Tool CLI** (O11 on-prem installation/administration) — [docs](https://success.outsystems.com/documentation/11/setup_outsystems_infrastructure_and_platform/setting_up_outsystems/unattended_installation_and_upgrade/configuration_tool_command_line_reference/); **Solution Pack Tool CLI** (O10 Java, solution deployment) — [docs](https://success.outsystems.com/Documentation/10/Setting_Up_OutSystems/Unattended_installation_and_upgrade/Unattended_Installation_and_Upgrade_for_Java/Solution_Pack_Tool_command_line_reference_for_Java/); **Cloud Connector (`outsystemscc`)**, Go, OutSystems-owned, networking — [repo](https://github.com/OutSystems/cloud-connector)

### Inferences
- There is no official "export my app as source code" button and no sign of one coming. The MCP positioning ("evolve in place — no migration, no replatform") reads as a deliberate retention strategy: OutSystems is opening the model to AI agents *inside* the platform boundary while keeping the exit path manual.
- The practical irony is that the same MCP that is pitched as a retention tool is the best-supported model-extraction channel ever shipped for OutSystems. `getDataModel` + `getScreen` + `getServerAction` + `listApps` + `runQuery` is, functionally, a reverse-engineering API — and the license/terms do not appear to restrict what you do with what you read.
- For portfolio-scale inventory, the combination is LifeTime API (what exists) + AI Mentor Studio API (what's wrong with it) + OSSYS metamodel via Advanced SQL (how the data is actually shaped). All three export cleanly. Logic does not.

### Gaps
- The **ODC Studio command line** page exists in the ODC documentation index but I could not retrieve its contents; its commands, flags, and whether it can export a module are unknown. This is the main unresolved official-tooling question for ODC.
- The OutSystems **Model API** reference documentation did not surface; I have no independent (non-OutSystems-repo) source for its full surface, rate limits, or terms of use.
- Whether AI Mentor Studio / Architecture Dashboard offers a bulk UI export (CSV/Excel) in addition to the API is unconfirmed.
- Whether the O11→ODC conversion tool produces a machine-readable report artifact (vs on-screen status) is unconfirmed — the official page is silent.
- Platform version coverage: I found nothing about reverse-engineering support for **OutSystems 10** beyond Discovery's "older versions for 10 and earlier"; O10 is effectively uncovered by current tooling.

## Q4 — Commercial migration vendors / AI-assisted modernization

### Takeaway
Two vendors make specific, technically coherent automated-conversion claims (**Adapt Systems** → React/Node from parsed OML; **Trivesit ACACIA** → Mendix from a landscape export), and neither has published a named client delivery. Everything else in this space is a services engagement with GenAI assistance, not a tool. I found **no independent verification of any end-to-end automated OutSystems conversion**.

### Cited Findings

**Adapt Systems — the most technically specific claim found**
- Claims to parse "OML (OutSystems' modeling language) into an intermediate representation covering entities, action-flow logic, screens, REST contracts, roles, client-side logic, timers, config, and cross-module dependencies" — i.e. an IR-based compiler architecture, not prompt-driven translation — [case studies](https://adapt-systems.com/case-studies)
- Reported sample results: source = **OutTracker, a public OutSystems Forge component** (not a client app); target = **React 19 + Node.js + SQL via Prisma**; 7 modules extracted, 103 files generated, 18 database models, 17 API modules, 17 frontend pages, JWT auth with role-based access (4 roles), **96% attribute coverage** with "the remaining 4% flagged for manual review rather than dropped", verified by **49 passing integration tests** that "compare behavior against the original" — [case studies](https://adapt-systems.com/case-studies)
- Credibility notes, in the vendor's own words: the page is "**One real sample migration. Honestly labeled as exactly that**", it is "a draft pending review", it says Adapt "has active and completed engagements it can't name yet", and "a live-engagement case study is planned but hasn't been published". **No named client, no pricing.** Entry point is a "Proof of Architecture Diagnostic" run on one of your own modules, starting with a discovery call — [case studies](https://adapt-systems.com/case-studies)

**Trivesit ACACIA (OutSystems → Mendix)**
- Claims it "automatically generate[s] Mendix applications, based on an export of your OutSystems landscape". Generates: "the entire domain model", "a module for data migration", "CRUD pages for all entities, with a basic admin/reader security model", "validation flows for entities and attributes, including fields such as zip code and e-mail", apps based on your own Mendix template, and multiple applications in parallel — [ACACIA page](https://trivesit.com/outsystems2mendix/)

### Inferences
- The vendor landscape splits cleanly on **what they do with logic**. ACACIA openly concedes it cannot export logic or layout — so it automates the schema-and-CRUD 30% and leaves the hard part. Adapt Systems claims to cover action flows and client logic in its IR, which is the materially harder and more valuable claim — and it is the one with the thinnest evidence (one public Forge app, self-labelled draft, no named client).
- Adapt's "96% attribute coverage" is a *data-model* metric dressed as a migration metric. 49 integration tests over 17 pages is light coverage for a behavioral-equivalence claim. The number to ask for is logic-node coverage: what fraction of action-flow node types does the IR actually lower, and what happens to the rest.
- Both automated vendors converge on the OML file as the extraction source, independently validating that OML→IR is the right architecture for a build. Neither mentions the Service Studio MCP/Model API, which suggests their pipelines predate it — a build-side opportunity.
- The "low-code exit" market is pre-commodity: no public pricing anywhere, no third-party benchmark, no analyst-verified delivery. Pricing is discovery-call-gated at every vendor found, which in practice means consulting economics, not tool economics.

- LowCodeMigration's site did not resolve; I cannot confirm the firm is currently operating.

- No vendor found that targets **ODC** as a migration *source* — all exit tooling found is O11/OML-era.

## Q5 — Generic reverse-engineering tooling that applies

### Takeaway
The genuinely load-bearing generic tooling is on the **database** side (SQL Server SMO + ScriptDom + SSDT, as actually used by `outsystems-ddl-exporter`), plus **MCP-driven AI agents** as the translation layer. .NET decompilation of generated assemblies is technically plausible but I found no source showing anyone doing it for OutSystems, so I will not assert it works.

### Cited Findings
- **SQL Server SMO** (object-graph DDL generation, "no regex/string-concat") and **ScriptDom** (T-SQL parsing, used to compare against DMM-produced DDL for "1:1 parity (PKs only, all `NOT NULL`)"), feeding **SSDT** as the eventual schema home — this exact combination is implemented and documented in `outsystems-ddl-exporter`, which also profiles the live database for "physical nullability, uniqueness, FKs, and data reality (NULLs, duplicates, orphans)" — [repo](https://github.com/danielbdyer/outsystems-ddl-exporter)
- Physical-schema naming facts that make DB-side RE necessary rather than optional: OutSystems "generates a physical table name for each entity", user tables carry the `OSUSR_` prefix and platform tables the `OSSYS_` prefix, and the logical→physical mapping is only in `OSSYS_ENTITY` — so a raw DB dump is unreadable without the metamodel join — [OutSystems Platform Metamodel](https://success.outsystems.com/documentation/how_to_guides/data/data_migration_from_production_to_non_production_environment/outsystems_platform_metamodel/); [forum](https://www.outsystems.com/forums/discussion/86587/get-entity-data-from-database-using-physical-table-name/)
- There is a standing community request for Service Studio to even *show* the physical table name for an entity — evidence that the mapping is deliberately hidden from developers — [OutSystems Ideas](https://www.outsystems.com/ideas/899/servicestudio-display-physical-database-table-name-for-a-given-entity/)
- **AI code-translation pipelines** are now first-class here: OutSystems' own `outsystems11-mcp` exists precisely to let Claude Code / Copilot / Cursor / Codex / Kiro / Antigravity read and reason over the application model, with documentation generation and dependency mapping named as supported uses — [repo](https://github.com/OutSystems/outsystems11-mcp). The DIY practitioner path (OutDoc export → AI assistant → .NET + React) is the documented low-tech version — [Medium](https://medium.com/@avidas.ca/how-i-turned-an-o11-app-into-react-net-without-rewriting-a-single-line-by-hand-17611902f8e1)
- On the target language of generated code: OutDoc's Forge page states it "is only available for the .NET stack of the OutSystems Platform", and a forum answer claims "Java is no more supported by OutSystems starting from OutSystems 11". The forum claim is a single community assertion and conflicts with the existence of OutSystems' own O11 Java-stack tooling (e.g. `OutSystems/linux-outsystemsplaform-scripts`, "Miscellaneous scripts for use with the OutSystems Platform J2EE stack"), so **treat the Java-stack status as contested** — [OutDoc](https://www.outsystems.com/forge/component-overview/159/outdoc-o11); [forum](https://www.outsystems.com/forums/discussion/85100/can-i-use-outsystems-to-develop-java-and-related-frameworks-like-springboot-apps); [J2EE scripts](https://github.com/OutSystems/linux-outsystemsplaform-scripts)
- Black-box / runtime RE of the deployed app: `OutSystems-Scan` demonstrated that a deployed Reactive/Mobile app can be probed from its public URL alone (`osscan.py -u <app url>`), which implies the client bundle and its API surface are externally enumerable — but the tool is archived and discontinued — [repo](https://github.com/5O4R3S/OutSystems-Scan)

### Inferences
- The database leg of a reverse-engineering pipeline is the one that is already solved with mature, generic, well-understood tooling (SMO/ScriptDom/SSDT/Prisma-style introspection). Budget effort accordingly: schema is cheap, logic is expensive.
- Reactive/ODC apps ship a JavaScript client bundle and consume generated REST/screen-data endpoints. That makes **runtime API-surface extraction** a legitimate third source alongside OML and metamodel — and the only source that captures what the app actually does at the wire level. No maintained tool does this; `OutSystems-Scan`'s archived existence is the proof of concept.
- A triangulated pipeline is strictly stronger than any single source: OML/Model-API for logic structure, OSSYS metamodel + physical DB for data truth, runtime endpoints for contract truth. Disagreements between the three are exactly where migration bugs hide.

### Gaps
- I found **no source** confirming that decompiling OutSystems-generated .NET assemblies (ILSpy/dotPeek/dnSpy) is practised or useful for OutSystems reverse engineering. The ResearchGate review's remark that exit code is "machine-generated" and hard to maintain is suggestive but is about delivered source, not decompilation. Do not assert decompilation as a viable path without testing it.
- Whether OutSystems' terms of service or EULA restrict decompilation, OML parsing, or metamodel querying — not researched; this is a legal question that should be checked before committing to a build.
- No maintained tool for extracting the Reactive/ODC client bundle or its generated API contracts.

## Q6 — Which combination gives the best coverage, and what are the gaps nobody covers?

### Takeaway
Best available coverage today is a four-source triangulation: **Service Studio MCP / Model API** for logic and screens, **`oml-utilities` → OML XML** for offline/batch structure, **Advanced SQL over the OSSYS metamodel (pattern per `outsystems-ddl-exporter`)** for the data model, and the **Platform Documentation API / OutDoc + AI Mentor Studio API + LifeTime API** for inventory, dependencies and quality signal. The uncovered gaps are batch/headless model extraction, the OML XML schema itself, UI-layout fidelity, and anything at all for ODC.

### Cited Findings (what each source actually contributes, per sources cited above)
- Logic + screens + data model, live and supported, one module at a time: `getDataModel`, `getScreen`, `getServerAction`, `runQuery`, `getValidationMessages`, `listApps` — GA — [outsystems11-mcp](https://github.com/OutSystems/outsystems11-mcp)
- Offline, batch-capable, whole-file: `oml manipulate <in> <out> --format xml` producing "a XML file … containing all fragments", plus `oml text-search` across a directory — but **last commit 2023-02-09** and version-pinned to platform versions it was built against — [oml-utilities](https://github.com/silviogarbes/oml-utilities)
- Data model with physical truth: Advanced SQL export to JSON + live-DB profiling for "physical nullability, uniqueness, FKs, and data reality (NULLs, duplicates, orphans)" + per-entity `CREATE TABLE` emission — [outsystems-ddl-exporter](https://github.com/danielbdyer/outsystems-ddl-exporter); subject to the platform blocking `OSSYS`/`OSUSR` references in Advanced SQL — [forum](https://www.outsystems.com/forums/discussion/23212/how-i-get-the-outsystems-data-schema/)
- Human-readable specs and diagrams: OutDoc, "an open implementation of the Platform Documentation API", producing "data model, reference/dependency, and process diagrams, plus details on processes, screens, actions, database" — **.NET stack only, O11 only** — [OutDoc](https://www.outsystems.com/forge/component-overview/159/outdoc-o11)
- Dependency rules and architecture indicators over time: Discovery 6.0.3, **O11, uploaded Sep 2023, no documented export** — [Discovery](https://www.outsystems.com/forge/component-overview/409/discovery-o11)
- Quality/risk prioritization, exportable via API into "other technical debt and BI tools" and usable "as a quality gate of an automated CI/CD pipeline" — [AI Mentor Studio API](https://www.outsystems.com/forge/component-overview/17621/ai-mentor-studio-api-o11)
- Portfolio inventory: LifeTime API v2, wrapped and maintained in `outsystems-pipeline` (Apache-2.0, last commit 2026-10-07) — [repo](https://github.com/OutSystems/outsystems-pipeline)
- ODC-readiness delta (if ODC is the target rather than the exit): O11→ODC Conversion Assessment Tool, GA Nov 2025, flags "code, data, and infrastructure patterns that won't carry over" — [product update](https://www.outsystems.com/product-updates/o11-to-odc-conversion-assessment-tool)

### Inferences — the recommended stack
1. **Inventory layer:** LifeTime API v2 via `outsystems-pipeline` → list of apps/modules/environments/teams. Cheap, supported, scriptable.
2. **Quality layer:** AI Mentor Studio API → findings per app/module, used to rank which modules to reverse-engineer first and to flag patterns that will not translate.
3. **Data layer:** the `outsystems-ddl-exporter` pattern (Advanced SQL over `OSSYS_ENTITY`/`OSSYS_ENTITY_ATTR`/`OSSYS_ESPACE` → JSON, plus live-DB profiling) → authoritative schema with real nullability/uniqueness/FK evidence rather than declared metadata. This is the most solved leg.
4. **Logic layer, interactive:** Service Studio MCP read tools + a coding agent → highest-fidelity logic and screen extraction, and the only *supported* channel. Use it to write and validate your IR spec.
5. **Logic layer, batch:** `oml-utilities` → OML XML for every module, parsed against the IR spec validated in step 4. This is where you must invest build effort, and where the schema risk lives.
6. **Human-facing specs:** call the Platform Documentation API directly (OutDoc as reference implementation) rather than scraping OutDoc output.

### Inferences — the gaps nobody covers
- **Headless, batch, CI-friendly model extraction.** The MCP needs Service Studio running on Windows with a module open and the server started manually; `oml-utilities` is batch-capable but frozen in 2023 and version-pinned. Nothing gives you "point at a factory, get 400 modules' logic as JSON". This is the highest-value thing to build.
- **A published OML XML schema.** `oml-utilities` hands you XML; no public source documents what is in it. Any OML-based pipeline carries unbounded schema-discovery cost plus per-platform-version regression risk.
- **UI layout and styling fidelity.** ACACIA states outright that "layout and logic cannot currently be exported"; OutSystems' own Traditional→Reactive guidance tells you to rebuild from scratch if UX changes; OutDoc documents screens but not pixel layout. No tool found claims faithful layout translation.
- **ODC as a reverse-engineering source.** Every extraction tool found — OutDoc, Discovery, `oml-utilities`, `outsystems-ddl-exporter`, the Service Studio MCP, Adapt's OML parser, ACACIA — is O11/eSpace-oriented. ODC tooling found is deployment-only (`odc-cli`, the remote tenant MCP). ODC also moves the database to Aurora PostgreSQL, invalidating the SQL-Server-specific DB leg.
- **OutSystems 10 and earlier.** Only Discovery mentions legacy-version builds. Older OML formats are covered, at best, by `oml-utilities`' version list.
- **Behavioral-equivalence verification.** Adapt's 49 integration tests are the only verification mechanism anyone described. No tool, open or commercial, offers a general harness for proving a converted app behaves like the original — which is the actual acceptance criterion for a migration.
- **Independent benchmarking of conversion vendors.** No third-party evaluation exists for any vendor in this space.

### Gaps (unanswered)
- Relative adoption of each tool is unmeasurable: Forge pages do not show download counts, and the GitHub star counts (4, 0, 23, 41) are too low to signal anything about production use.
- Whether a maintained fork or successor of `oml-utilities` exists privately (e.g. inside Adapt Systems or ACACIA) — their parsers are closed, so the real state of OML-parsing maturity is unobservable from outside.
- Legal/EULA constraints on OML parsing, metamodel querying and decompilation — not researched, and a prerequisite for a build decision.
- Analyst (Gartner/Forrester) positions on low-code lock-in and exit — not accessible in this research pass.
