# Generated Code & Decompilation: Recovering Readable Source from OutSystems Runtime Artifacts

Scope note: research conducted 2026-10-21. OutSystems 11 (.NET and Java stacks) plus ODC deltas. Primary sources are OutSystems official documentation (success.outsystems.com) and OutSystems Community forum threads; forum material is flagged as such. Where I could not verify a widely-repeated naming convention, it is listed under Gaps rather than asserted.

## Q1. What does the Platform Server generate when it compiles/publishes a module, and where does it land on disk?

### Takeaway
On a self-managed (on-prem / private-cloud) OutSystems 11 install, publishing a module produces a **full Visual Studio .NET project with generated C# source, plus compiled DLLs, .aspx/.asmx files and web resources** — and the platform *keeps all of it on disk* in two distinct places: the **compilation cache on the Deployment Controller** (`share\<module>\full`, which holds generated source) and the **deployed runtime files on each front-end** (`running\<module>.<versionid>`, which holds only binaries and resources). There is no need for a "keep generated source" flag: the source is a by-product the platform retains by design.

### Cited Findings
- Official disk-space guide, folder-by-folder (written explicitly "in the context of a Platform Server installed with the .NET stack version of the platform"):
  - `<platformserver>\share\<modulename>\full` — **full compilation cache**, Deployment Controller only. Contains **generated source (.oml, .cs, .csproj)**, release binaries (.dll, .aspx, .asmx) and resources (.js, .css, images) — [OutSystems 11 Docs: Guide to disk space usage and control on OutSystems Platform servers](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
  - `<platformserver>\share\<modulename>` — compressed **release application files package** consumed by Deployment Services; each module folder also holds the module file captured at the start of compilation, a folder with 1st- and 2nd-stage compilation results, and metadata files — [same source](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
  - `<platformserver>\share\<modulename>\partial\<developer>` — **partial compilation cache**, one set per developer, present only in **debug-enabled environments**; same file types as the full cache — [same source](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
  - `<platformserver>\running\<modulename>.<versionid>` — **release application files on the front-end**: `.dll`, `.aspx`, `.asmx`, `.js`, `.css`, images. Shared DLLs and JARs here are **hard links into `repository`**. More than one version folder can coexist (older/ready-to-deploy versions), cleaned automatically — [same source](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
  - `<platformserver>\repository\` — shared compiled libraries (**DLLs and JARs**) for public module and extension elements; can hold several versions of a producer module when consumers reference different versions — [same source](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
  - `<platformserver>\test\<modulename>\<developer>` — personal test area, front-end, debug-enabled environments only — [same source](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
  - `C:\windows\microsoft.net\framework\v4.0.30319\Temporary Asp.Net Files\<modulename>` (or `framework64`) — produced by the .NET Framework itself, not by the Platform Server — [same source](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
  - The guide warns release application files must never be deleted (an internal thread maintains that content), and that the `full` cache is required for 1-Click Publish of consuming modules — [same source](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
- Forum corroboration of the runtime layout and how to find it: apps run as .NET applications on IIS; find the physical directory via IIS console → Sites → Default Web Site → [app name] → Explore, e.g. under `Program Files\OutSystems\Platform Server\running`; that is where the platform "stores / deploys the generated compiled .Net files" and files there should not be deleted — [OutSystems Forum: source code of outsystems application](https://www.outsystems.com/forums/discussion/54881/source-code-of-outsystems-application/)
- Same thread: the `share\<eSpaceName>` contents are "source files" that are "useless and don't affect the app once it has been published" (i.e. deleting them does not stop a running app) — [OutSystems Forum: source code of outsystems application](https://www.outsystems.com/forums/discussion/54881/source-code-of-outsystems-application/)
- A **`bin2` folder exists under `running\{espace}`**: OutSystems staff note that assemblies are usually loaded by name rather than path, which avoids depending on `C:\Program Files\OutSystems\Platform Server\running\{espace}\bin2` — [OutSystems Forum: issue with dynamic linking .NET libraries in eSpace](https://www.outsystems.com/forums/discussion/22502/issue-with-dyanmic-linking-net-libraries-in-espace/)
- Deployment is two-phase: files are first copied to a pre-staging `share\<YourESpaceName>\full\bin` folder and then to the final `running\<YourESpaceName>\bin` folder (a 2019 thread about a copy failure between the two) — [OutSystems Forum: how to add resource which will be saved in bin instead of bin2](https://www.outsystems.com/forums/discussion/6712/how-to-add-resource-which-will-be-saved-in-bin-instead-of-bin2/)
- **Target framework**: the detach documentation states the generated solution is .NET Framework with a **4.7.2 minimum target**, built with **Visual Studio 2022**, published to **IIS**, and that the application pool should use ".NET 4.0" (i.e. CLR v4) — [OutSystems 11 Support: The detach process for OutSystems 11](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- **Java stack**: generated `.java` source also lands in a share folder — OutSystems staff and users in a Fortify SAST thread place it at `/opt/jbossas/server/outsystems/share`, with a per-module tree of the shape `<module>/src/os<module_name>/webservices/rpc/...` and generated files such as `WORLserviceErrorRecordList.java` — [OutSystems Forum: running Fortify scan on generated code (Java)](https://www.outsystems.com/forums/discussion/10392/running-fortify-scan-on-generated-code-java/)
- **Java stack caveat from OutSystems staff**: the share folder "doesn't contain all the source" — it is missing classes from the **OutSystems Runtime engine**, which produces missing-class errors in SAST; staff recommended the platform's "Detach Source Code" operation to get complete source including the runtime engine — [same thread](https://www.outsystems.com/forums/discussion/10392/running-fortify-scan-on-generated-code-java/)

### Inferences
- The `share` tree is the Deployment Controller's build workspace and the `running` tree is the IIS/app-server deployment target; therefore **a reverse engineer with filesystem access should always go to the controller's `share\<module>\full` first** (source + project files) and only fall back to `running\...` (binaries only) when they have front-end access.
- Because the full compilation cache contains the `.oml`, **filesystem access to a controller is effectively OML recovery**, which dominates any decompilation route (see Q6). This is the single highest-value finding for a reverse-engineering workflow.
- The `bin` / `bin2` split plus hard-linked shared DLLs in `repository` implies a reverse engineer collecting assemblies must dereference hard links (e.g. `tar -h`, as advised for the Java share folder in the Fortify thread) or they will collect stubs/duplicates.

### Gaps
- No official documentation found for the **Java-stack folder structure** equivalent to the .NET disk-space guide; the only Java paths I could source are from one old forum thread (JBoss-era, `/opt/jbossas/server/outsystems/share`). WAR/EAR/JAR naming for Java-stack modules is **not documented in anything I found** — the disk-space guide mentions JARs in `repository`/`running` but never `.war`/`.ear`.
- I could not verify from any source the exact **DLL file name** emitted per module (e.g. whether it is `<ModuleName>.dll`, `ss<ModuleName>.dll`, or similar). See Q3 Gaps.
- Whether OutSystems 11's newer .NET stack (post-11.18) ever targets .NET (Core) rather than .NET Framework: the detach doc only describes .NET Framework 4.7.2+, so treat "OutSystems 11 .NET stack = .NET Framework" as the documented position, not confirmed for every component.

## Q2. Does OutSystems ship generated C#/Java source files to disk? Is there a "keep generated source" flag?

### Takeaway
Yes — on **self-managed installations only**, generated source is written to disk on every publish with **no flag required**; `share\<ModuleName>\full` contains a complete Visual Studio .NET project. The nearest thing to a debug/retain-source setting is the environment's **debug-enabled** state, which additionally populates `share\<module>\partial\<developer>` and `test\<module>\<developer>`. I found **no** documented `GenerateDebugInfo`-style registry/config switch.

### Cited Findings
- The official OutSystems "Web_SAST" guidance is quoted in the forums as: "The source code can be found at `<PlatformInstallationFolder>\Platform Server\share\<ModuleName>\full`", that this folder holds **a Visual Studio .NET project and generated C#, ASPX, CSS and JavaScript files**, and that "Customers can take advantage of this and run SAST tools against this" — [OutSystems Forum: how extracting web and backend application source code?](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/)
- Same thread, quoting the same article: "**Source code can only be extracted with a self-managed installation**" — covering on-premises and private cloud, or hybrid setups that include self-managed environments — [same thread](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/)
- Cloud/PaaS environments give no IIS access, so the generated code is unreachable there; one 2021 forum questioner explicitly notes "no access to IIS servers on the cloud environment" — [OutSystems Forum: is it possible to get the Deployed Code (System Generated C# codes)](https://www.outsystems.com/forums/discussion/40860/is-it-possible-to-get-the-deployed-codesystem-generated-c-codes/)
- The generated source is listed as a documented artifact of the compilation caches (`.oml`, `.cs`, `.csproj`), and the **partial cache exists only in "debug-enabled environments"** — [OutSystems 11 Docs: disk space guide](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/)
- Any publish or model change **overwrites** code in these folders, since the platform always regenerates from the app definition — [OutSystems Forum thread set on viewing generated code](https://www.outsystems.com/forums/discussion/13350/view-generated-code/)
- The sanctioned, contractual route is the **detach process**, reachable in Service Center as a **"Modules Source Code" page** (older threads call it "Administration → Licensing → eSpaces Source Code"), described by OutSystems as "standard .NET code generated by the OutSystems Compiler" — [OutSystems 11 Support: The detach process for OutSystems 11](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/); forum reference to the Licensing menu path — [OutSystems Forum 40860](https://www.outsystems.com/forums/discussion/40860/is-it-possible-to-get-the-deployed-codesystem-generated-c-codes/)
- Detach preconditions and consequences (official): applies to **all** applications at once ("It is not possible to detach only some apps from OutSystems"); requires **Platform Server 11.18.1+**; is **irreversible**; OutSystems recommends staging Dev→Prod first because "generated code is tied to the environment it was compiled in" — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- Community reading of the commercial terms: detached code is available only when terminating the OutSystems contract/licence, and you may not modify generated code while still using the platform; under the PaaS agreement source can be extracted after a licence is cancelled (on-prem or cloud), the Free edition does not allow it, and you must go through an account rep or support ticket — [OutSystems Forum 40860](https://www.outsystems.com/forums/discussion/40860/is-it-possible-to-get-the-deployed-codesystem-generated-c-codes/); [OutSystems Forum 61645](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/)
- Extension (Integration Studio) source is retrievable directly via Integration Studio's **"Edit Source Code"** button — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/); extension source-file layout is documented separately — [OutSystems Help: About Extension Source Files](https://www.outsystems.com/help/integrationstudio/9.0/Getting_Started/About_Extension_Source_Files.htm)

### Inferences
- For a *technical* reverse-engineering exercise on a self-managed environment, **decompilation is usually unnecessary**: the `.cs`/`.csproj` (or `.java`) sources are already on the controller. Decompilation becomes the only route when you have **binaries only** — i.e. front-end-only access, a copied `running\...` or `repository\` folder, an exported `.oap`/package, or an extracted mobile app.
- The "debug-enabled environment" mechanism is the de facto "keep per-developer source" switch, since it is what causes `partial\<developer>` and `test\<module>\<developer>` trees to exist.

### Gaps
- No source found for a named flag such as `GenerateDebugInfo`, a registry key, or a documented `server.hsconf`/`OSHEComp.exe.config` switch that controls retention of generated source. Searches surfaced nothing; the only compiler setting I could verify in config/`OSSYS_PARAMETER` is `Compiler.DefaultPhysicalTableName` (see Q6).
- Whether PDB files are emitted alongside the DLLs in `share\...\full\bin` or `running\...\bin` is unverified. (This matters a lot: PDBs would make decompiler output far closer to the generated source.)

## Q3. How do the generated assemblies decompile? Which tools, and are symbols preserved?

### Takeaway
The generated output is **ordinary managed code** (C# DLLs plus `.aspx`/`.asmx` on IIS) and forum practitioners report decompiling it with standard tools (dotPeek, Reflector, and by extension ILSpy/dnSpy). I found **no evidence of obfuscation** and **direct testimony that developer-chosen names survive** (screen, entity and attribute names), though opinions split sharply on whether the result is maintainable. I found **no OutSystems-specific decompilation tooling, write-up or conference talk**.

### Cited Findings
- "The compiled output is a C# DLL and ASPX pages on the IIS application server, which can be decompiled with tools such as **dotPeek or Reflector**" — community member Devendra Baghel, who also characterises the result as "machine generated", "hard to understand and modify" — [OutSystems Forum 40860](https://www.outsystems.com/forums/discussion/40860/is-it-possible-to-get-the-deployed-codesystem-generated-c-codes/)
- Directly contradicting view in the same thread: Daniël Kuhlmann says the generated code **is readable, "shows your screen, entity, and attribute names"**, and can be maintained by a skilled .NET developer — [same thread](https://www.outsystems.com/forums/discussion/40860/is-it-possible-to-get-the-deployed-codesystem-generated-c-codes/)
- OutSystems' own characterisation of the detached output: "a standard, readable .NET solution with a documented folder structure", retaining "core functionality of apps built in Service Studio and Integration Studio"; modifications to it are "not supported by OutSystems" — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- Generated **extension** namespaces follow `OutSystems.Nss<ExtensionName>`: a 9.0 compile error references `System.Collections.Generic.ICollection<OutSystems.NssActiveDirectoryConnector.RCADUsersDisplayRecord>` — i.e. namespace `OutSystems.Nss` + extension name, with record wrapper types prefixed `R` — [OutSystems Forum: extension code written in .NET throwing an error after upgrading](https://www.outsystems.com/forums/discussion/14260/extension-code-written-in-net-is-throwing-an-error-after-upgrading/)
- Same thread: the 9.0 platform added an `OutSystems.Internal.Db` namespace import that 8.0 did not have (useful as a version fingerprint in decompiled code); extension DLLs are **lazy-loaded** into applications on demand; developers may use arbitrary namespaces inside their own extensions — [same thread](https://www.outsystems.com/forums/discussion/14260/extension-code-written-in-net-is-throwing-an-error-after-upgrading/)
- A **`<ModuleName>ReferencesProxy`** project/assembly is part of the generated solution, and for mobile there is a `MobileAppRefProxy` DLL (seen in a CS0016/CS0006 compile-error thread title) — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/); [OutSystems Forum: error cs0016 and cs0006 mobileapprefproxy dll](https://www.outsystems.com/forums/discussion/8455/error-cs0016-and-cs0006-mobileapprefproxy-dll-directory-invalid-not-found/)
- Decompiler tooling facts: **ILSpy** is an open-source (MIT) .NET assembly browser/decompiler producing C#/VB — [ILSpy on GitHub mirror listing](https://best-of-web.builder.io/library/icsharpcode/ILSpy); the **`ilspycmd`** CLI decompiles an assembly to console or an output directory, and `-p` emits a **compilable project** — [ilspycmd on NuGet](https://www.nuget.org/packages/ilspycmd)
- General decompiler caveat: output may be imperfect for complex or obfuscated assemblies, and comments plus original local-variable names are lost — [ILSpy alternatives/comparison listing](https://alternativeto.net/software/ilspy); [How does a decompiler work](https://main.palisade.email/learning/how-does-a-decompiler-work)
- Java-stack static analysis of generated `.java` works in practice but needs classpath help: a Fortify SCA run over the share-folder tarball parsed generated files such as `WORLserviceErrorRecordList.java`, failed on one file, and produced a report only after classpath entries were added; unresolved-function warnings remained — [OutSystems Forum: Fortify scan on generated code (Java)](https://www.outsystems.com/forums/discussion/10392/running-fortify-scan-on-generated-code-java/)

### Inferences
- Since the detached/generated solution is a *normal* VS solution compiled by the standard C# compiler with no obfuscation step mentioned anywhere in official docs, **ILSpy / dnSpy / dotPeek / JetBrains Rider's decompiler / .NET Reflector should all work with no special handling**, and `ilspycmd -p` is the practical way to bulk-convert a `running\<module>\bin` folder into browsable projects. For the Java stack, **CFR, Procyon, Fernflower (incl. via IntelliJ) and JD-GUI** are the standard equivalents — but note no source I found reports anyone actually decompiling OutSystems Java-stack JARs, because the `.java` source is already on disk.
- The two contradictory readability opinions are reconcilable: *identifiers* survive (so entity/attribute/screen/action names are recoverable), while *structure* is machine-shaped (deep nesting, generated state machines for flows, no comments) — so the code is greppable and analysable but not pleasant to maintain.
- The `R`-prefixed record types and `OutSystems.Nss*` namespaces are the clearest verified naming fingerprints; they suggest a systematic generator prefix scheme (which is consistent with, but does not prove, the commonly repeated `ss`/`rss` module-class prefixes).

### Gaps
- **I could not verify the `ssModuleName` / `rssModuleName` naming convention from any source.** Repeated targeted searches (including site-restricted searches on outsystems.com for `ssMainFlow`, `ssConstants`, `rssEspace`, and `ss` stack-trace fragments) returned nothing. The report should either omit these specific identifiers or label them as unverified folklore pending direct inspection of an assembly. The *verified* prefixes are `OutSystems.Nss<Extension>` (extension namespace) and `R<RecordName>` (record types), plus `<ModuleName>ReferencesProxy`.
- No published security research, conference talk, blog post or GitHub project specifically about decompiling OutSystems-generated code was found. Searches for OutSystems reverse-engineering/decompilation security research returned only generic .NET reverse-engineering material. This is a genuine absence of literature, not just a search failure — worth stating in the report.
- Whether OutSystems applies any obfuscation or `[Obfuscation]`/anti-tamper to its *own* runtime assemblies (`OutSystems.RuntimePlatform`, etc.) is unverified; note that the detach process ships these as **source projects**, which strongly suggests they are not protected in a way that would block analysis.

## Q4. Fidelity of the mapping back to the visual model — what survives and what is lost?

### Takeaway
The generated solution's folder structure is a near-1:1 projection of the module's *element tree* (Actions, Blocks, Entities, Structures, Roles, Exceptions, per-process folders, web services), so **named model elements and their logic are recoverable**. What is not represented anywhere in generated code is the *visual/diagrammatic* layer — node coordinates, flow layout, Service Studio metadata — and (by OutSystems' own account) all lifecycle tooling.

### Cited Findings
- The detached module project's subfolders are exactly: **`Actions`, `Blocks`, `Entities`, `Structures`, `ProcExc<ProcessName>`, `Exceptions`, `Roles`, `TypeFactory`, `WebServices`, `WebReferences`**, with a `<Project Name>.sln` at the root — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- The rest of the generated solution is the platform runtime shipped as source: top-level `Application` (`OutSystems.Application.Core`, `.Initialization.ASPNet`, `.ManifestGeneration`, `.Session`, `.Session.Abstractions`, `.Session.Persistent`), `DatabaseProviders` (`SQLServerDatabaseProvider`, `OracleDatabaseProvider`, `MySQLDatabaseProvider`, `PostgreSQLDatabaseProvider`, `iDB2DatabaseProvider`), runtime/platform projects (`OutSystems.CachingCommon`, `OutSystems.DebuggerClient`, `OutSystems.HubEdition.DatabaseAbstractionLayer`, `OutSystems.Logging`, `OutSystems.Logging.Database`, `OutSystems.ModuleServices`, `OutSystems.Plugin.FileBased`, `OutSystems.Plugin.RabbitMQ`, `OutSystems.PluginAPI`, `OutSystems.RESTService.Runtime`(+`.Abstractions`), `OutSystems.RuntimeCommon`, `OutSystems.RuntimePlatform`, `OutSystems.RuntimeSettingsConfiguration`, `OutSystems.Spreadsheet`), plugins/APIs (`Plugin.SAP` with `Runtime`/`RuntimeAPI`/`SapNcoConnectionManager`, `Plugin.Widgets.Runtime`, `REST.RuntimeAPI`, `RESTService.Runtime`, `Scheduler.Core`, `WebWidgets`, `WidgetsRuntimeAPI`), and `ThirdParty` (`GemboxSpreadSheet`, `Json.NET`, `SAP`, `WebApi2`) — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- **Timers / BPT activities / emails** are not in the module project: the **Scheduler Service source code is provided only on request** and is built from a separate `Scheduler.sln`, installed as a Windows service via `installutil scheduler.exe` from `\Scheduler\bin\Debug` ("Detached Scheduler Service") — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- **Mobile apps** split in two: the back-end detaches like a web module, while the **native Android/iOS shell is downloaded from the Applications page as a `tar.gz` that is kept only 7 days after a successful build** — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- Explicit losses stated by OutSystems: Service Studio, Integration Studio, Service Center, LifeTime and their visual development, ECT, monitoring and deployment features; **timer management reverts to direct database work** because Service Center is gone; **cross-module references must be managed manually by copying DLLs** (compile module B, copy all `.dll` from `B\bin` into `A\bin`); spreadsheet features need a GemBox licence; OutSystems-encrypted data must be decrypted before migration and `private.key` must be preserved — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- **Database artifacts are *not* delivered as a schema/data export**: the detach page supplies SQL UPDATE statements against OutSystems metadata tables (e.g. `OSSYS_SERVER`, `OSSYS_DBCONNECTION`) plus connection-string/config changes; for cloud customers "OutSystems does not provide a clone of the cloud database" — you copy your own data — [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- Server-vs-client split in O11: "Anything on the server is .net" — server actions, processes and data are server-side C#; client actions, screens and blocks in Reactive Web are JavaScript/HTML5/CSS3; IIS is the web server — [OutSystems Forum: OutSystems generated code architecture](https://www.outsystems.com/forums/discussion/64254/outsystems-generated-code-architecture/)

### Inferences
- Recoverable from generated code alone: **entity/attribute names and types, server action signatures and bodies, aggregate/SQL query text (as emitted SQL in the data-access layer), role definitions, exception handlers, exposed/consumed web services, structures, and per-process activity logic** (the `ProcExc<ProcessName>` folders mean BPT *logic* is generated, even though BPT *orchestration state* lives in the database and the Scheduler).
- Not recoverable from generated code: **flow diagram layout/coordinates, element descriptions and comments, the Service Studio widget tree as a design-time tree, theme/style-sheet editor state, dependency-manager metadata, and anything purely design-time**. These require the `.oml`.
- Because `<module>.oml` sits in `share\<module>\full`, in practice "what requires the OML" is only a blocker when you lack controller filesystem access (cloud/ODC) or only hold binaries.

### Gaps
- I found no official statement enumerating which model constructs are or are not represented in generated code; the above mapping is inferred from the detached solution's folder list, which is itself official.
- Traditional Web (Web Screen `.aspx`) vs Reactive Web (React/JS) fidelity differences are not documented in any source I located; the `.aspx` route plausibly preserves a widget tree far better than the React route, but this is unverified.

## Q5. Client side: generated JavaScript/HTML for Reactive Web and Mobile

### Takeaway
Reactive Web and Mobile screens/blocks/widgets are generated as **React components** and shipped as **optimized (minified) JavaScript**; community evidence indicates **source maps are not generated by the platform**, so browser-side recovery means reading minified React output. This is the weakest-documented area of the whole topic.

### Cited Findings
- OutSystems states that client-side logic is modelled visually and "**optimized JavaScript will be automatically created for you**", that **all screens, blocks and widgets are generated as reusable React components**, and that "secure and fast REST APIs to handle communication" are **automatically generated from the actions defined in the IDE** — [OutSystems blog: All you need to know about Reactive Web applications in low-code](https://www.outsystems.com/blog/posts/all-you-need-to-know-about-reactive-web); [OutSystems blog: Reactive Web Applications](https://www.outsystems.com/blog/posts/reactive-web-applications)
- Forum confirmation that "the reactjs framework is used for reactive web" — [OutSystems Forum: Reactive web development](https://www.outsystems.com/forums/discussion/56301/reactive-web-development/)
- **Source maps appear to be absent**: a thread about repeated "DevTools Failed to load source map" console warnings in Reactive apps concludes that the platform does not appear to generate the `.map` files, and that a fix would have to come from OutSystems. This is a community observation, not an OutSystems statement — [OutSystems Forum: how to fix DevTools failed to load source map warnings](https://www.outsystems.com/forums/discussion/85659/how-to-fix-devtools-failed-to-load-source-map-warnings/)
- Custom developer JavaScript is injected via the JavaScript element in client actions; OutSystems warns about direct DOM manipulation in Reactive Web and Mobile apps — [OutSystems 11 Docs: JavaScript](https://success.outsystems.com/documentation/11/integration_with_external_systems/javascript/)
- The `running\<module>.<versionid>` folder (and `share\...\full`) contains the served `.js` and `.css` assets, so on a self-managed server the shipped client bundles are directly readable from disk as well as over HTTP — [OutSystems 11 Docs: disk space guide](https://success.outsystems.com/documentation/11/managing_outsystems_platform_and_application_lifecycle/guide_to_disk_space_usage_and_control_on_outsystems_platform_servers/); [OutSystems Forum 61645](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/) (confirms JavaScript files among the generated artifacts)

### Inferences
- With minification but React component boundaries intact, client-side recovery should yield **screen/block/widget names, data-binding/variable names and client action logic** in a mangled but navigable form; standard tooling (Chrome DevTools pretty-print, `js-beautify`, `wakaru`/`react-devtools` component inspection) applies. Custom developer-written JavaScript blocks are likely the most readable part since they are embedded verbatim-ish.
- The auto-generated screen-data REST endpoints ("screen services") are an easier recovery surface than the JS itself: enumerating them from the network tab reveals the server action surface and payload structures without reading any code.

### Gaps
- No official documentation found for the generated client bundle layout, file naming, `/scripts/` bundle names, or whether minification is configurable. The notion that OutSystems ships no source maps rests on a single community thread.
- Whether the Mobile (Cordova/Capacitor shell) package contains the same unminified-or-minified assets as the web bundle, and whether the `tar.gz` native shell includes the JS bundle in readable form, is unverified.

## Q6. Generated database schema — physical names and reconstructing the data model from the DB alone

### Takeaway
User entities become `OSUSR_`-prefixed physical tables whose middle segment is, by default, a **hash of the eSpace name** (stable across environments); the authoritative logical↔physical mapping is the platform metadata table **`OSSYS_ENTITY`** (`Physical_Table_Name` column), with attributes in a related `Entity_Attr`/attribute table. The data model is therefore **largely reconstructible from the database alone**, via metadata rather than by parsing names.

### Cited Findings
- Mapping lives in **`OSSYS_ENTITY`**; the physical name is in the **`Physical_Table_Name`** column (also exposed as the `Physical_Table_Name` attribute of the System `Entity` entity). Looking up by logical name can return several rows because different eSpaces can define the same logical table name — [OutSystems Forum: logical physical table mapping](https://www.outsystems.com/forums/discussion/63151/logical-physical-table-mapping/); [OutSystems Forum: entity to physical table mapping](https://www.outsystems.com/forums/discussion/2943/entity-to-physical-table-mapping/)
- **Naming formats** and the `Compiler.DefaultPhysicalTableName` setting (three values):
  - `PREFIX_ESPACENAMEHASH_ENTITYNAME` — `OSUSR` prefix + **hash of the eSpace name**; hash is stable across environments; this is the default
  - `PREFIX_ESPACEID_ENTITYNAME` — legacy format `OSUSR_<ESPACE_ID>_ENTITYNAME`, e.g. entity `Client` in eSpace 112 → **`OSUSR_112_CLIENT`**
  - `ENTITYNAME` — no prefix/hash; the thread warns this weakens security because the Hub Server can no longer runtime-check table access, letting Advanced Queries reach other eSpaces' tables
  — [OutSystems Forum: configuring the physical table name format for entities](https://www.outsystems.com/forums/discussion/3444/configuring-the-physical-table-name-format-for-entities/)
- Where the setting lives: `OSHEComp.exe.config` in the Hub Server install root for ~3.2–4.0; **from 4.1 onward as a `Compiler.DefaultPhysicalTableName` row in the `OSSYS_PARAMETER` system table**. Services must be restarted; the change affects only entities created afterwards; OutSystems does **not** formally support the setting and advises against it — [same thread](https://www.outsystems.com/forums/discussion/3444/configuring-the-physical-table-name-format-for-entities/)
- Identifier length limits noted in that thread: Oracle table names ~18 chars with 12 reserved for suffixes; SQL Server ~233 chars from platform 5.0 — [same thread](https://www.outsystems.com/forums/discussion/3444/configuring-the-physical-table-name-format-for-entities/)
- **Renames do not rename tables**: renaming an entity changes the logical name while the physical table name can stay the same; a fresh deployment creates it under the new name — so physical names can differ per environment and must never be hardcoded — [OutSystems Forum: what happens in the database when an entity name is changed](https://www.outsystems.com/forums/discussion/66633/what-happens-in-the-database-when-an-entity-name-is-changed/); [OutSystems Forum: do table names change when deploying from dev to QA/production](https://www.outsystems.com/forums/discussion/26106/do-table-name-changed-when-deploying-from-dev-to-qa-production/)
- Metadata-driven reconstruction: the metamodel entity table carries an `Espace_Id` to filter per module, and attributes are in a separate attribute table (`Entity_Attr`) with an FK back to the entity table. An OutSystems staff member explains that logical (OML) and database names can differ, which is exactly why the mapping must be stored in metadata — [OutSystems Forum: get entities structures info list](https://www.outsystems.com/forums/discussion/36173/get-entities-structures-info-list/); [OutSystems Forum: create database documentation export](https://www.outsystems.com/forums/discussion/92421/create-database-documentation-export/)
- On OutSystems Cloud there is no direct DB access, so the usual route is to consume the **System** module's `Espace` / `Espace_Version` / entity metadata entities from inside an OutSystems module and filter by kind — [OutSystems Forum: in the metadata system where can I find the pages of an application](https://www.outsystems.com/forums/discussion/33770/in-the-metadata-system-where-can-i-find-the-pages-of-an-application/)
- Tooling: **SQL Map** (Forge) converts both directions, with an action `Conv_LogicalToPhysical` — [OutSystems Forge: SQL Map (O11) documentation](https://www.outsystems.com/forge/component-documentation/369/sql-map-o11/0); **Physical Database Mapping (O11)** shows entity↔table mappings — [OutSystems Forge: Physical Database Mapping (O11)](https://www.outsystems.com/forge/component-overview/19466/physical-database-mapping-o11); **Extended Metamodel (O11)** exposes additional metamodel entities but its author warns it "takes advantage of private and undocumented Platform APIs, which can change without notice" and may break on upgrade — [OutSystems Forge: Extended Metamodel (O11)](https://www.outsystems.com/forge/component-overview/2146/extended-metamodel-o11); **Entity Management Console (O11)** offers a read-only entity-structure view filterable by application/eSpace — [OutSystems Forge: Entity Management Console (O11)](https://www.outsystems.com/forge/component-overview/22616/entity-management-console-o11)
- Direct editing of the metadata tables is strongly discouraged — the platform may overwrite the record ("your changes will be overriden") — [OutSystems Forum: logical physical table mapping](https://www.outsystems.com/forums/discussion/63151/logical-physical-table-mapping/)
- Service Studio does not surface the physical name natively; it remains an open idea request — [OutSystems Ideas: Service Studio display physical database table name for a given entity](https://www.outsystems.com/ideas/899/servicestudio-display-physical-database-table-name-for-a-given-entity/)

### Inferences
- A database-only reverse-engineering path is viable and arguably the most robust one for cloud-hosted apps: join the metamodel (`OSSYS_ENTITY` + attribute table + eSpace tables) against `INFORMATION_SCHEMA` / `ALL_TAB_COLUMNS` to produce a logical ERD with real entity and attribute names, FKs and data types — without any code at all.
- Because the default physical name embeds a *hash of the eSpace name*, you cannot derive the module name from a table name by inspection alone (unlike the legacy `OSUSR_<id>_` form, where `<id>` joins to the eSpace table). Metadata lookup is mandatory for the default format.

### Gaps
- The hash algorithm behind `ESPACENAMEHASH` is not explained in any source found. Treat `OSUSR_<hash>_<ENTITY>` as opaque.
- Exact `OSSYS_ENTITY` / attribute-table column layouts, and the treatment of **views and stored procedures** generated by the platform (whether the platform emits views/sprocs for entities at all), are not documented in anything I located. Deletion/"soft-delete" columns, `_ID` sequence objects and index naming were likewise not covered by any source I found.

## Q7. ODC (OutSystems Developer Cloud) deltas

### Takeaway
In ODC the generated-artifact route essentially closes: the platform is **containerized and fully managed**, customers have no server/IIS/filesystem access, and there is **no documented detach process and no mechanism that produces an O11-style .NET solution**. Any ODC code extraction would be a contractual negotiation, not a self-service export.

### Cited Findings
- "There is currently no equivalent public mechanism that generates a traditional .NET solution package similar to O11"; ODC "doesn't follow the O11 model"; ODC is described as "containerized and fully managed", with deployment and execution layers abstracted away from customers; customers should not expect "a Visual Studio solution, standalone database scripts, or an O11-like structure"; any detachment "would likely be a contractual arrangement with OutSystems" — [OutSystems Forum (Nov 2025): Detachment process from OutSystems ODC — any guidance or experience?](https://www.outsystems.com/forums/discussion/105782/detachment-process-from-outsystems-odc-any-guidance-or-experience/)
- "There is no official detach process available nor documented for ODC" (Daniël Kuhlmann, MVP) — [same thread](https://www.outsystems.com/forums/discussion/105782/detachment-process-from-outsystems-odc-any-guidance-or-experience/)
- The O11 detach documentation is explicitly an **OutSystems 11 Support/Licensing** page and has no ODC counterpart in the documentation set — [The detach process for OutSystems 11](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)
- ODC does document an **External Libraries SDK** for custom code (i.e. the supported way to inject and therefore read/own C# in ODC) — [ODC Documentation: External libraries SDK README](https://success.outsystems.com/documentation/outsystems_developer_cloud/building_apps/extend_your_apps_with_custom_code/external_libraries_sdk_readme/)
- On OutSystems Cloud (O11 PaaS) the same access barrier already applies: no IIS access, therefore no reachable generated code; extraction is "only with a self-managed installation" — [OutSystems Forum 61645](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/)

### Inferences
- For ODC, the viable reverse-engineering surfaces are: the **ODC Portal/ODC Studio model itself** (and any OML/ODC app export the customer can make), the **auto-generated screen-data REST endpoints and client bundles observable from the browser**, the **external libraries** the customer authored, and **metadata queried from inside an app**. Server-side binaries and generated C# should be assumed unavailable.
- The practical rule to state in the report: *the .NET/Java decompilation route is an **O11 self-managed** technique.* On O11 cloud it degrades to client-side + database + metadata; on ODC it degrades further to client-side + in-app metadata.

### Gaps
- No source found describing ODC's runtime technology stack at the artifact level (container images, whether per-app code is still C#, whether anything is retrievable through the ODC API). The Nov-2025 forum thread is the most current material I could find and it is explicitly non-authoritative.
- Dated as of research: no 2026 ODC detachment documentation existed in anything I could reach.

## Cross-cutting: published write-ups and tools specific to OutSystems decompilation

### Takeaway
There is effectively **no published literature** on decompiling OutSystems-generated code — no conference talk, no security-research post, no dedicated GitHub tool surfaced across multiple search formulations. The practical knowledge base is (a) OutSystems' own detach documentation, (b) scattered forum threads, (c) SAST-oriented guidance that points at `share\<module>\full`, and (d) Forge metadata-mapping components.

### Cited Findings
- Searches for OutSystems-specific reverse engineering/decompilation research returned only generic .NET reverse-engineering material (e.g. NetSPI's `binrev` for chaining .NET decompilation in pentests) with no OutSystems content — [NetSPI: binrev — automate reversing Windows binaries for pentesters](https://www.netspi.com/blog/entryid/196/binrev-automate-reversing-windows-binaries-for-pentesters)
- The closest thing to an officially-blessed "read the generated code" use case is **SAST scanning**: OutSystems' Web_SAST guidance tells customers to point SAST tools at `share\<ModuleName>\full` (.NET) and, for Java, staff direct customers to the Detach Source Code operation because the share folder lacks the runtime engine — [OutSystems Forum 61645](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/); [OutSystems Forum 10392](https://www.outsystems.com/forums/discussion/10392/running-fortify-scan-on-generated-code-java/)
- Third-party commentary is unreliable and contradictory: a UK G-Cloud supplier listing describes a documented detachment process yielding "a standard .NET solution" — [G-Cloud service listing](https://www.applytosupply.digitalmarketplace.service.gov.uk/g-cloud/services/462854692013187) — while a migration-vendor blog claims OutSystems apps "compile to a proprietary runtime with no source export" — [rapidevelopers: Migrating OutSystems to Code](https://www.rapidevelopers.com/md/no-code-to-code/how-to-migrate-outsystems-project-to-code). The vendor blog's claim is **contradicted by OutSystems' own detach documentation**; prefer the official page.
- A community account states O11 detachment "generates a full .NET solution bundle, including database scripts, projects, runtime components, and infrastructure elements" — this **partially conflicts** with the official page, which supplies metadata UPDATE statements and config changes rather than a database schema/data export — [OutSystems Forum 105782](https://www.outsystems.com/forums/discussion/105782/detachment-process-from-outsystems-odc-any-guidance-or-experience/) vs [detach doc](https://success.outsystems.com/support/licensing/the_detach_process_for_outsystems_11/)

### Inferences
- The absence of literature plus the presence of plain on-disk source explains why no OutSystems-specific decompiler exists: for the population with access (self-managed admins), decompilation is redundant; for the population without access (cloud/ODC), binaries are unreachable, so a decompiler would have nothing to chew on.

### Gaps
- I did not find any GitHub repository, OWASP/BSides/Black Hat talk, or vendor security advisory analysing OutSystems generated assemblies. Report this as "no published work found as of October 2026" rather than "none exists".
