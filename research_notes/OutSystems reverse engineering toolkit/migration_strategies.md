# Migrating OFF OutSystems: Strategies, Methodologies, and Case Studies

> Scope note for the report writer: evidence on this topic is **thin and heavily vendor-skewed**. There is no neutral, named-client, fully quantified case study of an OutSystems → conventional-stack migration in the public record as of this research. The strongest *primary* sources are (a) OutSystems' own data-migration how-to guides and forum answers about the detachment process, and (b) open-source tooling that reads the OutSystems metamodel. Almost all timeline/cost numbers come from competitors or migration vendors and are labelled as such throughout. Several URLs below (arXiv ids `2602.*`, `2605.*`, `2609.22719`, a ResearchGate "2026" review) were returned by search with 2026 dates; I could not independently verify the 2026-dated arXiv bodies (PDF streams were undecodable / HTML not fetched), so they are flagged as unverified.

## 1. What is the canonical migration playbook, and what order do practitioners recommend?

### Takeaway
There is **no published canonical OutSystems-exit playbook** from any neutral source. The only officially documented, step-ordered OutSystems migration procedure is the **data** migration guide (environment-to-environment, not platform-exit), and its ordering is directly reusable as the data phase of an exit. Everything upstream of data (inventory → model extraction → logic → UI) is documented only in vendor/tool-vendor pipelines, which converge on a three-stage shape: **parse model → intermediate representation → generate code + verify**.

### Cited Findings
- OutSystems' official data-migration guide prescribes a strict 9-step order: (1) inventory source entities by Solution/Application/eSpace including all producer dependencies; (2) match entity and attribute **physical** names via `SS_Key` + eSpace `SS_Key` — "It's extremely important to keep in mind this match if using any query to push data"; (3) match **static entity** record identifiers (they differ between environments); (4) disable BPT triggers; (5) create/update users and groups and retain mappings; (6) migrate application data **ordered by FK dependency**; (7) migrate hybrid BPT instances (`OSSYS_BPM_*`) after mapping process/activity/role/tenant ids; (8) re-enable BPT triggers by migrating `OSEVT_*` data with FKs remapped; (9) enable applications — after which "Timers and Processes run again" — [OutSystems docs-howtos, data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- The one published end-to-end extraction pipeline with stated stages (Adapt Systems, a migration tool vendor) is: (1) parse OutSystems source (**OML**) into a structured intermediate representation covering *entities, action-flow logic, screens, REST contracts, roles, client-side logic, timers, config, and cross-module dependencies*; (2) generate idiomatic target code from that IR; (3) verify with integration tests that compare behaviour against the original — [Adapt Systems case studies](https://adapt-systems.com/case-studies) (page is marked draft pending review)
- Academic work on low-code interoperability uses the same shape — a **pivot metamodel** (B-UML, from the BESSER framework; UML for data models + IFML for UI) with per-platform in/out pipelines, explicitly one-directional (each direction needs its own pipeline) — [Alfonso, Conrardy & Cabot, "Towards the interoperability of low-code platforms", arXiv:2412.05075v1, Dec 2024](https://arxiv.org/html/2412.05075v1)
- Research on LLM code translation argues the IR step is what preserves intent: direct one-shot translation "often loses program intent," and a language-neutral plan covering I/O, types and loop bounds should precede generation — [arXiv:2602.16106](https://arxiv.org/html/2602.16106) *(2026-dated, body not independently verified)*; a companion comparison of pseudocode / natural-language / graph / compiler-style IRs found **natural-language IR the strongest central layer** despite being least formal — [arXiv:2605.25232](https://arxiv.org/pdf/2605.25232) *(2026-dated, unverified)*
- Betty Blocks (competitor) states the O11→ODC path has **no automated conversion tool** and that traditional web apps "must be manually rebuilt as reactive web apps, screen by screen" — [Betty Blocks, O11 to ODC cost breakdown](https://bettyblocks.com/blog/outsystems-11-to-odc-migration-cost) and [Betty Blocks, migrate off low-code without a full rebuild](https://bettyblocks.com/blog/how-to-migrate-off-a-low-code-platform-without-a-full-rebuild) — vendor source
- General modernization decision framework (not OutSystems-specific): start from the business requirement and the constraint blocking it, then choose refactor vs. bounded replacement vs. full replacement; full replacement requires "an agreed inventory of required capabilities, data migration feasibility, and evidence that narrower options are insufficient" — [Software Modernization Services: refactoring vs rewriting](https://softwaremodernizationservices.com/insights/refactoring-vs-rewriting-code/)

### Inferences
- The *data* phase ordering is the only part of an exit that OutSystems itself has de-risked and documented; a practical exit playbook should lift that ordering wholesale and treat the "destination environment" as the new stack's database.
- Because `SS_Key` is the stable cross-environment identity (not name, not id), any exit tooling must key its inventory and mapping tables on `SS_Key` from the start, or re-runs and incremental cutovers will silently mis-join.
- The convergence of the tool vendor, the academic pivot-metamodel work, and the LLM-translation literature on **model → IR → generate → verify** is the single most defensible structural claim available; it is convergence of approach, not of measured outcome.

### Gaps
- No practitioner-authored, neutral ordering for the *pre-data* phases (inventory → logic → UI). I found no conference talk, no r/outsystems or r/ExperiencedDevs thread, and no consultancy engineering blog with a sequenced exit playbook. Searches targeting Reddit returned no Reddit results at all.
- No published guidance on whether to exit module-by-module (strangler) vs. big-bang, with measured outcomes either way.

## 2. Which artifacts are the highest-value extraction targets, and in what order?

### Takeaway
The data model is the only artifact that is cleanly, officially, and programmatically extractable (via the `ossys_*` metamodel plus the physical SQL catalog). Integrations and extensions are partially recoverable (extensions can contain real C# source — but only optionally, and only through a GUI). Business logic and UI are the least extractable and are where every source says the effort concentrates.

### Cited Findings
- **Data model — highest value, fully automatable.** The open-source `outsystems-ddl-exporter` extracts the OutSystems logical data model via a *single* "Advanced SQL" export, reading `ossys_Entity` and `ossys_Entity_Attr` (surfacing `originalName`, logical `dataType`, and the external connector's `external_dbType`), reconciles that against the physical catalog (`sys.columns`, `sys.foreign_keys`), and emits one JSON payload structured as **modules → entities → attributes, relationships, indexes**, plus SSDT-ready one-CREATE-TABLE-per-entity scripts with inline PKs, defaults, FKs, indexes and `MS_Description` extended properties — [outsystems-ddl-exporter](https://github.com/danielbdyer/outsystems-ddl-exporter)
- **Entity → physical table inventory** is a documented metamodel query: "Use the Entities query to list physical table names per Espace" — [OutSystems data-migration guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **Roles** are extractable from the metamodel and cross-matched on eSpace `SS_Key` + Role `SS_Key` — [OutSystems how-to-migrate-data](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/11-how-to-migrate-data.md)
- **Timers / processes / site properties / web services / locales** are extractable in bulk via Forge documentation components: OutDoc "can extract information related to the modules and automatically generate documentation," and the **OutDoc Release Report** variant gathers, organised by element, information about *Processes, Timers, Site Properties, Web Services and Locales*, exported to Excel — [OutDoc Release Report (O11), OutSystems Forge](https://www.outsystems.com/forge/component-overview/8508/outdoc-release-report-o11); a second component, **DOC Assist**, "facilitates the documentation of site properties, processes, and timers" with Excel export — [DOC Assist (O11)](https://www.outsystems.com/forge/component-overview/17661/doc-assist-o11)
- **Timer semantics to carry over:** timers are executed by the OutSystems Scheduler Service, which polls for ready timers; each timer carries a timeout in minutes (max wait for execution to end), **default 20** — [OutSystems 11, Using Timers](https://success.outsystems.com/documentation/11/building_apps/using_timers/) / [Timer reference](https://success.outsystems.com/Documentation/10/Reference/OutSystems_Language/Processes/Timer/)
- **In-flight BPT state** must be inventoried before any cutover: use `OSSYS_BPM_Process` and `OSSYS_BPM_Activity` filtered by `IS_TERMINAL = 0` to see what is still running — [how-to-migrate-data](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/11-how-to-migrate-data.md)
- **Screens / UI are the bottleneck, not a cheap extract.** A 2021 Universidade Nova de Lisboa thesis on OutSystems legacy→reactive migration found UI was "the most prioritized feature but also the major bottleneck"; the author ultimately decided not to pursue the project — [Romão 2021, UNL](https://run.unl.pt/bitstream/10362/130408/1/Romao_2021.pdf)
- **Screen-level metadata worth capturing** includes screen name, screen title and **user roles** per screen — [ODC Screens documentation](https://success.outsystems.com/documentation/outsystems_developer_cloud/building_apps/user_interface/screens/)
- Adapt Systems' sample migration enumerates what their IR covered and in what quantity for one 7-module Forge app: **18 database models, 17 API modules with 35 business-logic methods, 17 fully implemented frontend pages, 8 client hooks, 11 typed external API clients, JWT auth with 4 roles, 103 generated files, 96% attribute coverage, 49 passing integration tests** — [Adapt Systems](https://adapt-systems.com/case-studies) (vendor self-reported, sample app not a client engagement)

### Inferences
- A defensible extraction order follows extractability and dependency: **(1) data model + physical schema → (2) roles/permissions → (3) integration contracts → (4) timers/BPT/site properties → (5) screen inventory with per-screen roles → (6) action-flow logic → (7) expressions and client-side logic.** Items 1–5 are mechanisable today; 6–7 are where AI assistance and human review are actually needed.
- Because OutDoc/DOC Assist export to Excel, the cheap first pass at inventory does not require writing any OML parser — a point worth making to teams who assume they must reverse the binary format first.
- The 96% attribute coverage figure is for *attributes* (the easiest artifact class) on a small public Forge app; it should not be generalised to logic or UI coverage, and the vendor's own framing ("the remaining 4% is flagged for manual review, not silently dropped") is a coverage claim, not a correctness claim.

### Gaps
- No published data on what fraction of *business logic* (action flows, expressions) any tool recovers correctly — only the single vendor's "35 business logic methods" count with no accuracy measure.
- I could not confirm from primary sources whether OutDoc exports a complete **screen inventory** (search results covered processes/timers/site properties/web services/locales but were silent on screens); the OutDoc Forge page should be checked directly.

## 3. Data migration: how do you get the data out, and what are the gotchas?

### Takeaway
Direct database access against the `OSUSR_*` physical tables, driven by metamodel queries over `OSSYS_ENTITY` / `OSSYS_ENTITY_ATTR`, is the officially documented route. The dominant gotchas are **identity**: nothing can be joined on names or ids across environments (only `SS_Key`), every foreign key must be remapped through an explicit mapping table in dependency order, and **soft keys are not remapped at all**.

### Cited Findings
- **Cross-environment identity.** Entity and attribute matching is done via `SS_Key` combined with eSpace `SS_Key`; "Espace and Entity `SS_Key` values stay the same across environments and identify the same object in each" — [data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **FK remapping is mandatory and ordered.** The guide prescribes an auxiliary "FKs-Map" table recording source→destination id pairs keyed by eSpace, Entity and Attribute `SS_Key` ("an auxiliary supporting table (temporary or not) mapping and matching entity identifiers between source and destination environment… used to replace the foreign keys on the destination accordingly to the map"). Remapping must respect dependency order because "it's not possible to insert records with foreign keys that weren't already migrated and mapped on FK-Map." For **cyclic dependencies**, leave the optional FK empty on insert and update in a second pass. **Self-referencing keys** need a post-insert update — e.g. `PARENT_ACTIVITY_ID` updated after activities migrate, `TOP_PROCESS_ID` after the process record — [data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **Soft keys are a silent trap.** "Soft-Keys (SKs) aren't mapped and replaced automatically like the Foreign-Keys (FKs)," which can affect runtime behaviour — [data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **Static entities.** "Static Entities are managed by the OutSystems Platform and must not be changed" — but their *record identifiers* used as FKs can differ between environments and must be mapped early — [data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **Binary / BLOB attributes.** Discover them with a metamodel query filtering `attribute.TYPE` to `BinaryData`; example output is given as physical-table/column pairs (e.g. `OSUSR_s41_FeedbackScreenshot | ImageBinary`). "These take up significant disk space and take time and resources to migrate" and must be planned separately — [how-to-migrate-data](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/11-how-to-migrate-data.md)
- **Users.** Find User foreign keys across active entities via a pattern query over `OSSYS_ENTITY_ATTR` (eSpace `SS_Key` + User entity `SS_Key`), then pull stored identifiers per consumer entity, e.g.:
  ```sql
  SELECT distinct(UserId)
  FROM OSUSR_s41_LastFeedback
  WHERE UserId IS NOT NULL
  ```
  Users are matched by **username**, groups by **name** — [how-to-migrate-data](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/11-how-to-migrate-data.md)
- **Event / BPT tables.** `OSEVT_*` event entities have a fixed structure: `_ESPACE_ID`, `_TENANT_ID`, `_ACTIVITY_ID`, `_PROCESS_DEF_ID`, `_IS_UPDATE`, `_IS_LIGHT`. `Is_Update` indicates whether an event is queued for the OnUpdate or OnCreate schedule and "matters for 'wait' and 'conditional start' activities." BPT triggers cannot be disabled in cloud environments; the documented workaround is to `DELETE` destination event rows before migrating — the guide's own example is `DELETE FROM OSEVT_ORDER`, with **no WHERE clause** — [how-to-migrate-data](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/11-how-to-migrate-data.md)
- **Disabling the app.** Service Center → Factory → Applications → *Disable*: web pages then show "Application Temporarily Unavailable," web services return an "offline" error, timers stop, and BPT stops processing `OSSYS_BPM_EVENT` / `OSSYS_BPM_EVENT_QUEUE`. **Triggers remain active** while disabled; queued records are processed after re-enabling — [how-to-migrate-data](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/11-how-to-migrate-data.md)
- **Cloud DB permissions are restricted.** "In Cloud the permissions are limited to Data-reader and Data-writer" — [data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **Other explicit warnings:** unique indexes "can't be repeated" and must be handled by the migration process; do not migrate site properties/settings/configuration/integration endpoints across environments; data volume "directly impacts migration duration and can result in service downtime"; dirty or duplicate destination data distorts "calculations, metrics, dashboards"; platform and database engine versions should match — [data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **Underlying databases are standard.** Apps run on MS SQL Server, Azure SQL and Oracle — [OutSystems evaluation guide, standard architecture](https://www.outsystems.com/evaluation-guide/standard-architecture-with-no-lock-in/)
- **Physical naming and inactive columns.** Physical tables carry the `OSUSR_` prefix (e.g. `OSUSR_ABC_CUSTOMER`); the DDL exporter by default projects names back to logical form — "`dbo.OSUSR_ABC_CUSTOMER` becomes `dbo.Customer`." Inactive/deleted attributes are detectable and excludable: "columns flagged `isActive = false` or `physical.isPresentButInactive = 1` are omitted from emission by default while remaining in the decision log for audit trails." OutSystems `IsIdentifier` drives the primary key (policy signal: "PK (OutSystems `IsIdentifier`) ⇒ `NOT NULL`"). FK constraints only materialise when the database confirms them — "`reference_hasDbConstraint` and relationship `hasDbConstraint` only flip to `1` when the logical reference is backed by a matching `sys.foreign_keys` entry"; cross-catalog FKs are not created and FKs with orphaned rows are withheld. System/external tables such as `OSSYS_User` are **not** in the export and must be supplied via supplemental model files — [outsystems-ddl-exporter](https://github.com/danielbdyer/outsystems-ddl-exporter)
- **The `OSUSR_` prefix is a known annoyance**, with a standing community idea to shorten it — [OutSystems Ideas #712](https://www.outsystems.com/ideas/712/platform-reduce-user-table-prefixes-from-osusr-to-os-only/)
- **Anecdotal volume signal (AWS Marketplace reviewer):** importing more than 100K records "took hours," worked around with C#/Java extensions — [AWS Marketplace, OutSystems Platform Self-Managed reviews](https://aws.amazon.com/marketplace/reviews/reviews-list/prodview-r7elneqdgaftu?page=40) — *anecdotal, single reviewer*
- Community threads exist on both directions of external-DB data movement — [Migrating Data from OutSystems to an external database](https://www.outsystems.com/forums/discussion/85706/migrating-data-from-outsystems-to-an-external-database/); [Data migration from legacy DB to OutSystems](https://www.outsystems.com/forums/discussion/65396/data-migration-from-legacy-system-database-to-outsystems-application-database/) — *forum, anecdotal*

### Inferences
- The FK-Map + dependency-ordered insert pattern that OutSystems documents for environment-to-environment migration is **exactly** the pattern an exit needs; the only change is that the "destination" is your new schema. Teams who skip it and try a straight `bcp`/`SELECT INTO` will corrupt referential integrity, because OutSystems identifiers are environment-local autonumbers.
- The orphaned-FK and `hasDbConstraint` findings in the DDL exporter are the practical confirmation that **OutSystems' logical references are frequently not enforced in the physical database** — so an exit must expect dirty referential data and must decide, per relationship, whether to tighten or carry the mess forward.
- `isActive = false` columns are a *schema*-level soft-delete of attributes. I found **no** primary-source documentation of a platform-wide row-level `Is_Active` soft-delete convention for business entities; the only `Is_Active` sighting was in a supplemental `User` example (alongside `Creation_Date`, `Last_Login`), i.e. on `OSSYS_User`-like system tables. Treat "OutSystems soft-deletes your rows via Is_Active" as **unverified** — it appears to be a *developer* convention in many apps rather than a platform behaviour.
- Cloud tenancy is the hard constraint on the whole exit: with only data-reader/data-writer, you cannot disable triggers, cannot create helper objects freely in the platform DB, and may be unable to run bulk-export utilities — pushing teams toward REST/OData extraction or toward negotiating a database copy.

### Gaps
- **No primary documentation of a complete list of OutSystems-managed columns** on `OSUSR_*` tables. The DDL exporter README explicitly does not provide one, and the OutSystems guides do not enumerate them. This is a real gap for anyone writing an extractor.
- **No documentation found of multi-tenancy column handling in an exit.** Tenancy appears only as `_TENANT_ID` on `OSEVT_*` rows and a tenant entry in the FKs-Map; how `TENANT_ID` on multi-tenant business entities should be projected into a new schema is not covered by any source I found.
- No published guidance on extracting data via **Service Center** or platform **REST APIs** as an alternative to direct DB access; all official material assumes DB access.
- No measured throughput figures (GB/hr, rows/hr) for any extraction method.

## 4. Integrations: recovering REST/SOAP contracts and extensions (.xif / C#)

### Takeaway
**Yes — extensions can contain real C# (or Java) source code, but it is optional and not programmatically extractable.** Only binaries are required for an extension to work, OutSystems ships some of its own connectors with the implementation hidden in a DLL, and the only supported way to get at source is to open the `.xif` in Integration Studio's GUI (no CLI). Consumed/exposed REST and SOAP contracts are recoverable from the model (the one published IR covers "REST contracts"), but I found no primary-source procedure for bulk-exporting them.

### Cited Findings
- Opening a `.xif` in Integration Studio "produces a folder with the extension's source code"; after compiling once "you can locate the folder that is created in the disk next to the .xif file" — [Programmatically extract source code from xif](https://www.outsystems.com/forums/discussion/85629/programmatically-extract-source-code-from-xif/), [Is it possible to access C# code of an extension?](https://www.outsystems.com/forums/discussion/85074/is-it-possible-to-access-c-code-of-an-extension/) — *forum answers*
- **No CLI.** "There don't seem to be any command line arguments available for Integration Studio, unlike Service Studio," so scripted unpacking is not straightforward; community workarounds suggested were AutoHotkey or UiPath (i.e. GUI robots) — [forum 85629](https://www.outsystems.com/forums/discussion/85629/programmatically-extract-source-code-from-xif/) — *anecdotal*
- **Source is optional; sometimes deliberately hidden.** "Adding source code to extension is completely optional, only binaries are needed," and on "the OutSystems built AWS connectors you will note that they 'hide' their implementation in a dll" — [forum 85074](https://www.outsystems.com/forums/discussion/85074/is-it-possible-to-access-c-code-of-an-extension/) — *anecdotal but technically consistent with the documented workflow*
- Official workflow is GUI editing with an external IDE: Integration Studio's role is "editing and updating the extension source code as well as ensuring that it remains synchronized in both Integration Studio and Microsoft .NET or Java"; users report clicking "Edit Source Code which will open the C# Code in IDE (Can be Visual Studio)" — [Overview of Integration Studio](https://www.outsystems.com/help/IntegrationStudio/9.1/Getting_Started/Overview_of_OutSystems_Integration_Studio.htm); [Extension Source Files, OutSystems 11 docs](https://success.outsystems.com/Documentation/11/Extensibility_and_Integration/Extend_Logic_with_Your_Own_Code/Extension_Source_Files)
- **Container formats:** `.xif` and `.oml` are described by community members as proprietary/undocumented, whereas **`.oap` files can be opened with archivers like 7-Zip** — and renaming `.oap` to `.zip` and unzipping reportedly yields the contained `.oml` files — [How to get file oml from oap file](https://www.outsystems.com/forums/discussion/73988/how-to-get-file-oml-from-oap-file/), [Can I see the source code of .oml file](https://www.outsystems.com/forums/discussion/76283/can-i-see-the-source-code-of-oml-file/) — *forum, anecdotal*
- **OML format is contested in community sources:** one thread calls it "an XML representation of the visual elements in a module," another describes it as a binary file format, and a Forge extension exists that converts the OML binary to XML — described as "similar to what OutDoc already does, but exporting more detail," with a companion component (author: "at a very early stage") intended to provide an OML-like API over that output; another reply notes "a simplified version of that XML is retrievable, tools like OutDoc make use of it" — [Inspect the OML file](https://www.outsystems.com/forums/discussion/5476/inspect-the-oml-file/), [Read and Display OML File as Text](https://www.outsystems.com/forums/discussion/96092/read-and-display-oml-file-as-text/) — *forum, conflicting*
- **The supported programmatic route into the model is Service Studio's Model API, not OML parsing.** A community CLI, `oml-cli`, "build[s] and edit[s] OutSystems 11 modules safely through Service Studio's Model API," reads modules via that API and "never edits OML XML," and offers an architecture view built from `.oap`/`.oml` files — [Topurrra/oml-cli](https://github.com/Topurrra/oml-cli)
- A third-party low-code migration analysis asserts the Model SDK (JS/TS) gives "access to the application model for a semi-automated migration" — [Netguru, Mendix vs OutSystems](https://www.netguru.com/blog/mendix-vs-outsystems) — *vendor-adjacent; I did not locate official Model SDK documentation to corroborate*
- The one published migration IR explicitly includes **REST contracts** and "11 typed external API clients" among generated outputs — [Adapt Systems](https://adapt-systems.com/case-studies) — *vendor*
- OutDoc Release Report enumerates **Web Services** per module to Excel — [OutDoc Release Report](https://www.outsystems.com/forge/component-overview/8508/outdoc-release-report-o11)

### Inferences
- Extensions are the **best-case** artifact in an exit when source is present (it is real, idiomatic .NET/Java you can lift almost verbatim) and the **worst-case** when it is not (DLL-only, requiring decompilation or black-box reimplementation). An early inventory step should therefore be: for every `.xif` in the factory, does a source folder materialise on open? That single boolean materially changes the estimate.
- The absence of an Integration Studio CLI means extension extraction cannot be put in CI. Practically: a one-time, human-driven sweep that dumps every extension's source folder into git before the migration starts.
- `.oap` → zip → `.oml` plus the Service Studio Model API is the realistic extraction stack; writing a from-scratch OML binary parser is the path tool vendors took but is not necessary for teams that can drive the Model API.

### Gaps
- No primary-source method for **bulk-exporting consumed/exposed REST and SOAP contracts** (e.g. regenerating OpenAPI/WSDL for every integration in a factory). Adapt Systems claims their IR captures them but publishes no method.
- No documentation found on recovering the configuration of **consumed REST** endpoints (base URLs, auth, headers) as opposed to their schemas — and site properties/integration endpoints are precisely what OutSystems says *not* to migrate between environments, implying they live in configuration not model.
- I could not verify the existence or scope of an official "Model SDK" for O11/ODC from OutSystems documentation.

## 5. AI/LLM-assisted migrations in 2025–2026: pipelines, success rates, where they break

### Takeaway
AI-assisted OutSystems exit is real but **evidentially immature**: one named vendor pipeline with self-reported structural-coverage metrics on a small public sample app, one individual's single-session anecdote, and academic work that explicitly reports **no accuracy figures** for its LLM step. Every source that evaluates LLM-mediated model migration qualitatively reports the same failure mode: missing or wrong elements, especially relationships and anything beyond the data model.

### Cited Findings
- **Vendor pipeline with numbers (sample app, not a client):** OML → structured IR (entities, action-flow logic, screens, REST contracts, roles, client-side logic, timers, config, cross-module dependencies) → idiomatic code → integration-test verification against the original. Reported on one 7-module Forge app ("OutTracker"): **96% attribute coverage** with "the remaining 4% flagged for manual review, not silently dropped," **49 passing integration tests**, 103 files, 18 DB models, 17 API modules / 35 business-logic methods, 17 screens, 8 client hooks, 11 typed API clients, JWT + 4 roles. Target stack React 19 + Node.js + Prisma/SQL. **No LOC, no timeline.** — [Adapt Systems](https://adapt-systems.com/case-studies) *(vendor self-reported; page marked draft)*
- **Individual anecdote:** a developer exported an Expense Manager app's structure with **OutDoc**, then used Claude Code (and/or SASVA) to generate a React frontend and .NET backend, reporting a running React + .NET application "in a single session" — [Medium: How I Turned an O11 App into React + .NET Without Rewriting a Single Line by Hand](https://medium.com/@avidas.ca/how-i-turned-an-o11-app-into-react-net-without-rewriting-a-single-line-by-hand-17611902f8e1) — *anecdotal, single small app, not independently verified; the article itself returned 403 to automated fetch so details come from the search snippet*
- **Academic LLM-in-the-loop pipeline, no success rate published.** Alfonso/Conrardy/Cabot use visual LLMs (GPT named) to convert a platform screenshot into **PlantUML**, then PlantUML → B-UML pivot model, prompting with LCP-specific syntax context; PlantUML is chosen deliberately "because the LLM has seen more of it in training." Where partial exports exist, the LLM is given them and asked to add missing elements, "typically associations." The paper reports **no accuracy, precision, recall, or success-rate figures**. Two qualitative demos: Mendix→PowerApps via Excel (model incomplete because PowerApps' import lacks relationships, which must be added manually) and PowerApps→Oracle Apex via LLM ("some elements are missing or wrong"). Summary claim: "Regardless, the data model has been successfully transferred and requires little completion by the user." Platforms surveyed: Mendix, OutSystems, PowerApps, Appian, ServiceNow, Salesforce, Pegasystems, Zoho, ReTool, Oracle Apex — [arXiv:2412.05075v1](https://arxiv.org/html/2412.05075v1)
- **Stated limitations of that work:** only data models implemented (UI and behavioural migration is future work); most tools ignore generalizations, association classes and enumerations; the Excel route is lossy (infers types/relationships from spreadsheet structure, loses explicit validation rules); **LLM output is nondeterministic so completeness and correctness are not guaranteed** — [arXiv:2412.05075v1](https://arxiv.org/html/2412.05075v1)
- **Agentic requirements recovery (adjacent, relevant to the "spec/IR" stage):** "From Code to Requirements: Agentic Reverse Engineering of Business Rules at Enterprise Scale," Agrawal, Das, L, N, Sarvade, Manivanan, Joshna, Kalyansundaram — arXiv:2609.22719v1, cs.SE/cs.AI, CC BY 4.0, metadata-dated 2026-09-22. Described as agentic tooling that drafts business requirements from code, tests and configuration for undocumented enterprise systems, with human review at escalation points; it frames the problem as "the absence of formal requirements artifacts forces teams into expensive, knowledge-losing manual reverse engineering." **I could not extract its evaluation or any quantitative results** (PDF streams undecodable) — [arXiv:2609.22719](https://arxiv.org/pdf/2609.22719) *(2026-dated; results unverified; search noted it as vendor-affiliated)*
- **IR choice matters, per translation literature:** one-shot LLM translation "often loses program intent," motivating a language-neutral algorithm plan (I/O, types, loop bounds) before generation — [arXiv:2602.16106](https://arxiv.org/html/2602.16106); a comparison of IR families found **natural-language IR the strongest central layer** — [arXiv:2605.25232](https://arxiv.org/pdf/2605.25232); compiler-IR pivots (LLVM IR, TransCoder-IR) avoid training a source→IR step — [arXiv:2310.11476](https://arxiv.org/pdf/2310.11476); IRCoder reports grounding code models in shared compiler IR improves code understanding and generation — [IRCoder, ACL 2024](https://aclanthology.org/2024.acl-long.802.pdf) *(the 2026-dated arXiv bodies are unverified)*
- **Closest peer-reviewed low-code precedent:** a 2023 ECBS paper migrated a low-code *generator* from JavaScript to TypeScript by having an LLM convert sub-generators separately, keeping the migrated system testable via automata learning and model analysis — [Towards LLM-based System Migration in Language-Driven Engineering, ECBS 2023](https://www.idt.mdu.se/ecbs2023/pre-prints/paper_2497.pdf)
- **OutSystems' own automation is assessment-only.** In November 2025 OutSystems released the **O11→ODC Conversion Assessment Tool**, the first component of an **App Conversion Kit**; it runs on the customer's own O11 infrastructure and flags code, data and infrastructure patterns that won't carry over. Commentary: "assessment is automated. Conversion largely is not," and OutSystems "is still building automation for parts of the conversion." A 2024-era description of the planned kit said it would ingest "your existing O11 app portfolio (apps, modules, and extensions) converting them into ODC applications," while a partner noted the kit would have "some limitations in certain areas due to the very high level of complexities of code required" — [Medium: Before you plan an O11 to ODC conversion, run this tool first](https://medium.com/@nelsonrapinto/before-you-plan-an-o11-to-odc-conversion-run-this-tool-first-ce265fbd4ef0); [Medium: Migrating from O11 to ODC and sneak peek on the migration kit](https://medium.com/@ut_markes/migrating-from-o11-to-odc-and-sneak-peek-on-the-migration-kit-39b1e3e9ea7d); [dbiz.ai ODC migration](https://dbiz.ai/insights/odc-migration)
- **Platform context affecting urgency:** per community reporting of ONE 2025, "O11 and ODC are being unified as a single platform" and "O11 support has been extended indefinitely" — [Medium/@ut_markes](https://medium.com/@ut_markes/migrating-from-o11-to-odc-and-sneak-peek-on-the-migration-kit-39b1e3e9ea7d); this conflicts with a review site's claim that O11 support lasts "until at least March 2027" — [RapidDev](https://www.rapidevelopers.com/review/outsystems) *(unsourced in that article; treat the end-of-support date as unsettled)*

### Inferences
- **Where AI breaks down, consistently across sources: relationships/associations, advanced type constructs, and everything that is not the data model.** The data model is the part AI least needs help with (it is deterministically extractable from `ossys_*`); the parts AI is being asked to do — action flows, expressions, UI — are the parts with zero published accuracy data. The honest statement for the report is that **no published success rate exists for AI-assisted business-logic or UI migration off OutSystems.**
- The sensible 2026 architecture is **deterministic extraction where a model exists, LLM only for the gaps**: metamodel SQL for schema, Model API/OML for flows and screens, LLM for expression translation, naming, idiomatic restructuring and test synthesis — with generated integration tests as the verification gate (the one design choice both the vendor pipeline and the ECBS paper share).
- Adapt Systems' "integration tests that compare behavior against the original" is the only published *verification* mechanism; its 49 tests on a 17-screen app is roughly 3 tests/screen, which is a weak behavioural net. This is the number most worth scrutinising in the report.
- OutSystems releasing an *assessment* tool but not a *conversion* tool for its own O11→ODC path is strong indirect evidence that automated conversion of OutSystems logic is hard even for the vendor with full model access — a useful prior for anyone promising automated exit to a foreign stack.

### Gaps
- **No independently verified success rate for any AI-assisted OutSystems exit.** No benchmark, no multi-app study, no error taxonomy.
- No published data on token/compute cost, human-review hours per screen, or defect rates post-cutover for AI-assisted migrations.
- SASVA (referenced in the Medium anecdote) was not investigated; its capabilities and provenance are unverified here.

## 7. OutSystems' licensing, exit terms, and "data portability" commitments

### Takeaway
OutSystems publicly commits to **source-code detachment** — "if you stop using the platform, you can detach the source code of your applications" and manage it as any other .NET application — but community and forum evidence establishes three hard limits: detachment is **contractually gated on terminating the subscription**, it is **not self-service** (you contact OutSystems), and the public commitment **says nothing about data export, data portability, or exit assistance**. The usability of the detached code is disputed, with the only accounts of it coming from parties selling migrations.

### Cited Findings
- **The public commitment.** The platform "takes your application models and generates standard .NET applications" that run on a standard web application server; "if you stop using the platform, you can detach the source code of your applications," then manage it "as any other .NET application, using the IDEs and version control systems you choose." Apps run on standard databases (MS SQL Server, Azure SQL, Oracle) — [OutSystems evaluation guide: Standard architecture with no lock-in](https://www.outsystems.com/evaluation-guide/standard-architecture-with-no-lock-in/)
- **What that page does NOT say (verified absences):** no mention of data export, data portability, or exit assistance; no statement of whether the "extra OutSystems services" that complement front-end servers are required post-detachment; the detachment statement sits in the section covering OutSystems Cloud and OutSystems 11 and is **not explicitly extended to ODC**; contractual exit terms are not included (the page only links to a Master Subscription Agreement) — [OutSystems evaluation guide](https://www.outsystems.com/evaluation-guide/standard-architecture-with-no-lock-in/)
- **Detachment is subscription-termination-gated and gated on a support request.** OutSystems' stated position per forum answers: "it is only allowed to detach the applications generated code if you had an Agile Platform subscription active and chose to stop using the Agile Platform"; a user who found no detach option in Service Center was told "the detachment process for this eSpace can only be executed when you decide to terminate your Agile Platform subscription. If you want to detach the source code please contact us." — [Detach OutSystems applications](https://www.outsystems.com/forums/discussion/5528/detach-outsystems-applications/), [Detach source code without terminating subscription](https://www.outsystems.com/forums/discussion/10554/detach-source-code-without-terminating-outsystems-subscription/), [Detachment Process](https://www.outsystems.com/forums/discussion/101173/detachment-process/), [Get the source code from OutSystems without stopping use of the platform](https://www.outsystems.com/forums/discussion/82134/get-the-source-code-from-outsystems-without-stop-the-use-of-the-platforme/) — *forum answers spanning ~2013–2025; verify against current terms*
- **Edition and environment restrictions:** source code cannot be extracted from the Free version; detaching cannot be done in a Personal Environment — [forum 7344](https://www.outsystems.com/forums/discussion/7344/re-cannot-download-source-code-of-the-application/), [forum 5528](https://www.outsystems.com/forums/discussion/5528/detach-outsystems-applications/) — *anecdotal*
- **The unofficial back door (self-managed/on-prem only):** generated C# lives in the Platform Server's **share folder**; forum answers note that code is "not commented, and is instrumented with extra code for debugging purposes," and suggest a hybrid route — "take the library code from the detach tutorial and the eSpace code from the share folder." This requires file-system access, i.e. on-premise/self-managed — [View generated code](https://www.outsystems.com/forums/discussion/13350/view-generated-code/), [Is it possible to get the deployed code (system generated C#)](https://www.outsystems.com/forums/discussion/40860/is-it-possible-to-get-the-deployed-codesystem-generated-c-codes/), [How to extract web and backend application source code](https://www.outsystems.com/forums/discussion/61645/how-extracting-web-and-backend-application-source-code/) — *forum, anecdotal*
- **Disputed usability of detached code.** A migration vendor argues OutSystems' code export is not a usable exit route, calling the output "unreadable, full of broken dependencies, and won't compile without weeks of work" — [LowCodeMigration](https://lowcodemigration.com/) — *vendor with direct commercial interest; treat as a claim, not a finding.* A review site asserts more strongly that "Neither O11 nor ODC provides any source-code export that runs outside OutSystems," concluding exit means rebuilding every app from scratch — [RapidDev](https://www.rapidevelopers.com/review/outsystems) — *unattributed in the article and in direct conflict with OutSystems' own published statement; flag the conflict rather than picking a side.*
- **Commercial lever during exit:** "departing clients can seek changing the licensing model to minimize the cost while transitioning" — [Netguru](https://www.netguru.com/blog/mendix-vs-outsystems) — *vendor-adjacent*
- **Pricing structure as the lock-in mechanism:** AO (Application Object)-based pricing raises switching cost as the portfolio grows; practitioners quoted as "constantly cutting corners because of additional license cost" and "At renewal, they've got you" — [RapidDev citing lowcodemigration.com practitioners](https://www.rapidevelopers.com/review/outsystems) — *second-hand quotes from a vendor site; anecdotal*
- **Academic/literature framing:** a critical literature review describes the gap between the "no vendor lock-in" promise and the real-world difficulty of maintaining the code after leaving the platform — "The OutSystems Low-Code Platform Between Vendor Promises and Practical Evidence: A Critical Study of Scaling and Exit Readiness" — [ResearchGate 407425757](https://www.researchgate.net/publication/407425757_The_OutSystems_Low-Code_Platform_Between_Vendor_Promises_and_Practical_Evidence_A_Critical_Study_of_Scaling_and_Exit_Readiness_An_analytical_literature_review_based_on_peer-reviewed_work_and_practitio) — *ResearchGate returned 403 to automated fetch; I could not verify the abstract, authorship, venue, peer-review status or any of its findings. Report writer should either fetch it manually or cite it only as "a literature review exists" with that caveat.*
- **A user review states flatly:** "there's no exit strategy in OutSystems" — surfaced via [PeerSpot OutSystems reviews](https://www.peerspot.com/products/outsystems-reviews) — *single anonymous reviewer, anecdotal*
- **Counter-context — vendor's data stance on inbound migration:** OutSystems' own modernization page says data migration is handled through professional services or partner engagements, and pitches isolating legacy logic and migrating in waves — [OutSystems Legacy Modernization](https://www.outsystems.com/initiatives/legacy-modernization) — *this is about moving ON to the platform; notable that even inbound data migration is positioned as a services engagement*
- OutSystems has separately marketed openness: a 2025-era announcement framed a new open AI platform as cutting vendor lock-in — [CFOtech AU](https://cfotech.com.au/story/outsystems-launches-open-ai-platform-to-cut-vendor-lock-in) — *press release coverage; about AI model choice, not application portability*

### Inferences
- The detachment commitment is real as *stated* but is structured so it cannot be used as a migration tool: you cannot detach to evaluate feasibility while still subscribed, so **no team can test the quality of its own escape hatch before committing to terminate.** That asymmetry is the practical core of the lock-in, independent of code quality.
- Because detached code is generated, uncommented, and debug-instrumented (per forum accounts of the share folder), it is better understood as a **behavioural reference and a safety net** than as a codebase to maintain — i.e. it supports verification of a rebuild, not avoidance of one.
- **Data portability is the stronger lever than code portability**: the database is standard SQL Server/Azure SQL/Oracle, and the official data-migration guides effectively document how to extract it. A team's exit risk is therefore concentrated in logic and UI, not data — the opposite of how the "detach the source code" framing suggests.
- For ODC specifically, the absence of any explicit detachment statement combined with cloud-only data-reader/data-writer permissions means **ODC tenants should assume a weaker exit position than O11 tenants** until OutSystems states otherwise in writing.

### Gaps
- **The Master Subscription Agreement's actual exit, data-return and transition-assistance clauses were not retrieved.** This is the single most important remaining gap for the report — any contractual claim should be sourced from the MSA directly.
- No official statement found on whether **ODC** supports source-code detachment at all.
- No official OutSystems documentation of the detachment procedure itself (steps, outputs, what is excluded) — only forum references to a "detach tutorial."
- No documented exit-assistance or transition-services offering, priced or otherwise.

## 8. Counterpoint: when is reverse engineering the wrong approach?

### Takeaway
No source addresses this question for low-code exits specifically. The transferable general finding is that reverse engineering is the *fallback* when requirements are lost, not the preferred method — and the OutSystems-specific evidence (UI as the dominant bottleneck, platform-provided features with no equivalent, zero published logic-translation accuracy) suggests a hybrid: reverse-engineer the data and contracts deterministically, re-specify the UI and workflows from requirements.

### Cited Findings
- Reverse engineering is framed in the literature as working backward to recover design and behaviour from an existing application, versus forward engineering from a requirements/design baseline — [GeeksforGeeks, forward vs reverse engineering](https://www.geeksforgeeks.org/difference-between-forward-engineering-and-reverse-engineering/), [EPAM: What is reverse engineering in software engineering](https://solutionshub.epam.com/blog/post/what-is-reverse-engineering-in-software-engineering)
- Practitioner rule of thumb for choosing rewrite: favour rewriting when the system *also* has performance problems, changes often, or is a core company asset; and note that "Nobody knows exactly the requirements anymore so you'll have to reverse engineer from the code the behavior," with tests "often missing or trivial" — [Paul Borile, "The 'Fix it or rewrite it from scratch' dilemma"](https://paulborile.medium.com/the-fix-it-or-rewrite-it-from-scratch-dilemma-486423edf8e0) — *individual practitioner opinion*
- Reverse engineering is also advocated as a **requirements-gathering technique** in its own right, including for large software purchases — [CIO: Reverse engineering, the most powerful requirements gathering technique of all](https://www.cio.com/article/246598/reverse-engineering-the-most-powerful-requirements-gathering-technique-of-all.html), [CIO: Use reverse engineering to help users set requirements](https://www.cio.com/article/239039/use-reverse-engineering-to-help-users-set-requirements-for-big-software-purchases.html)
- Decision gate for full replacement requires "an agreed inventory of required capabilities, data migration feasibility, and evidence that narrower options are insufficient" — [Software Modernization Services](https://softwaremodernizationservices.com/insights/refactoring-vs-rewriting-code/)
- **OutSystems-specific evidence that argues against literal UI reverse engineering:** UI was "the most prioritized feature but also the major bottleneck" in an OutSystems migration study, whose author abandoned the project — [Romão 2021, UNL](https://run.unl.pt/bitstream/10362/130408/1/Romao_2021.pdf)
- **Platform-provided features that must be rebuilt** are visible in what the migrations had to recreate: JWT auth with role-based access replacing platform roles (4 roles) and typed clients replacing platform-managed integrations — [Adapt Systems](https://adapt-systems.com/case-studies); timers replaced by whatever schedules in the new stack, given that OutSystems timers are run by the platform's Scheduler Service with its own timeout semantics — [OutSystems Using Timers](https://success.outsystems.com/documentation/11/building_apps/using_timers/); BPT process/activity state has no generic equivalent and is explicitly treated as "hybrid" platform-managed data — [data-migration-guide](https://github.com/OutSystems/docs-howtos/blob/master/src/data/data-migration/10-data-migration-guide.md)
- **Model-level fidelity is lossy even between low-code platforms:** most tools "ignore advanced constructs such as generalizations, association classes, and enumerations," and the spreadsheet route "loses explicit validation rules" — [arXiv:2412.05075v1](https://arxiv.org/html/2412.05075v1)
- An agentic-requirements-recovery paper frames manual reverse engineering as "expensive, knowledge-losing" — i.e. the motivation for tooling is that the human version of this is the costly path — [arXiv:2609.22719](https://arxiv.org/pdf/2609.22719) *(2026-dated, body unverified)*
- A Hacker News commenter's framing that reverse engineering "has always been without code" was surfaced but is a general remark, not migration guidance — [HN 45400762](https://news.ycombinator.com/item?id=45400762) — *anecdotal, low value*

### Inferences
- The evidence supports a **split strategy rather than a single answer**: reverse-engineer what is deterministic and expensive to re-decide (schema, data, integration contracts, roles, timer schedules, screen *inventory*); re-specify from requirements what is cheap to re-decide and expensive to replicate faithfully (screen *layout and widgets*, platform-idiom workflows, BPT processes).
- Reverse engineering is the wrong primary approach when (a) the OutSystems app heavily uses platform widgets/features with no target equivalent, (b) the app encodes accumulated low-code workarounds rather than business intent, or (c) the organisation retains the domain experts — in which case re-specification is faster and produces a better system. It is the right approach when domain knowledge has left the building, which practitioner accounts describe as the common case.
- The most valuable product of a reverse-engineering pass may not be code at all but an **auditable capability inventory** that satisfies the full-replacement decision gate and doubles as the estimation basis — which also addresses the complete absence of public per-screen effort data.

### Gaps
- **No experienced-migrator recommendation specific to low-code exit** was found: no conference talk, no consultancy engineering blog, no practitioner thread weighing reverse engineering against clean-room rewrite for OutSystems. This is the largest qualitative gap in the research.
- No published comparison of outcomes between the two approaches on comparable OutSystems portfolios.
- Specific named pitfalls from the assignment — hidden logic in **expressions**, **Aggregates → SQL** translation fidelity, and platform widgets with no equivalent — have **no published documentation or measurement** that I could find. They are plausible and consistent with the lossiness findings above, but should be presented as expected risks, not as sourced findings.
